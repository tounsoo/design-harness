# @design-harness/web

The design-harness app: a project's prototype rendered as a board of live frames, with `@design-harness/core`'s checks beside it. It runs entirely in the browser. A static build works with no backend, and projects are kept in the browser's IndexedDB.

The left panel is the agent's chat, on the person's own Anthropic API key: ask the agent to build or change the prototype, and the frames and the checks follow, with the agent fixing what the checks report. A plain code view edits the same files by hand.

## Run it

```sh
npm ci                # from the repository root
npm run dev           # Vite dev server for apps/web, after building the local package source
npm run build         # static build in apps/web/dist/, the local package source included
npm run e2e           # builds, then runs the end-to-end tests in Chromium
```

`npm run vendor` (run by `dev`, `build` and `e2e`) prebuilds the packages a frame imports from this repository's `node_modules` into `public/vendor/` (git-ignored). `npm run check` at the root typechecks, lints and runs the unit tests, the app's included.

On first open the app seeds the Nook example from `packages/core/examples/nook/`: its config and its legal booking prototype, read from the files core's own tests read. The seed adds two views to core's two: the desktop and the phone again in the dark scheme, so "AA in light and dark" is something the board shows. What you see:

The canvas is the product, and everything else is a panel around it: the chat on the left, the checks and code on the right, each collapsible and resizable. With less room than a desktop the shell changes layout ([widths](#widths)); nothing is lost, only moved.

- **Header:** the project (a picker once the browser holds more than one) and prototype, a quiet badge on a stored TSX prototype ("TSX, read-only"; see [TSX prototypes, notice only](#tsx-prototypes-notice-only)), the Canvas, Variants, Project and Proposals views as a Todae `ToggleGroup` named Main view, one button pressed (the Variants button shows how many variants the open prototype has, the Proposals button how many proposals are open; the arrow keys move between the buttons, and Space or Enter presses one), New prototype, New project ([New project](#new-project)), and icon buttons, named in their tooltips, for Export (the project file), Import and Export code (the open prototype as a runnable React project, [Code export](#code-export)), then Canvas only and the panel toggles. New prototype makes an empty spec prototype with a name; there is no format to choose. A project whose library has no part description cannot check a spec, so there the dialog says so and makes nothing.
- **Panels:** the chat and the checks and code sit in Todae Splitters, after Todae's app-shell recipe. Each hides and shows from its header button, its own close button, Enter on its handle, or a shortcut: Ctrl+B (⌘B on a Mac) for the chat, Ctrl+Alt+B (⌥⌘B) for checks and code. Drag a handle, or focus it and use the arrow keys, to resize. Whether each panel is open and how wide it is are kept per viewer in this browser's localStorage (`design-harness.panels`) and restored on load; blocked storage only means they last for the visit.
- **Canvas only:** the header and both panels step aside, and a floating bar keeps the prototype's name, zoom, a quiet verdict and **Show panels**. Ctrl+. (⌘.) or the header's button turns it on and off, and Escape leaves it. Focus moves to Show panels on the way in and back to the toggle on the way out, and a screen reader hears each change.
- <a id="widths"></a>**Widths:** `shell-width.ts` reads the window's width as one of four layouts and sets it on the shell as `data-width`; the least width of each is a harness token (`harness.shell.tablet`, `.laptop`, `.desktop`: 40, 64 and 80 rem), read from the page's style, so `app.css` holds no breakpoint of its own.
  - **Desktop** (80 rem and wider): everything above, unchanged.
  - **Laptop** (64 to 80 rem): every pane and one header row. New prototype, New project, Export, Import and Export code move into a Todae `Menu`, **More actions**; Canvas only and the panel toggles stay as buttons.
  - **Tablet** (40 to 64 rem): the header is two rows, the title and the actions over the view buttons. There is room for the canvas and one panel, so opening the chat closes the checks and code, and the other way round. Canvas only's bar sits above the board, not over it, here and on a phone, where it takes more than one row. It opens with the chat if the stored panels have it open, else the checks.
  - **Phone** (narrower than 40 rem): one pane at a time, the canvas first. A panel toggle, its shortcut, or anything that sends you to a panel (Ask the agent to fix, Show in code) shows that panel across the whole width in place of the canvas; the toggle again, the panel's close button, a view button, or anything that points at the canvas (Show me, a note's Show me, pin mode) brings the canvas back. Canvas only joins the More menu, with its shortcut beside it, and focus comes back to the menu's button on the way out; The mark and the slash leave the header, and the pickers may be narrower (`harness.size.picker-compact`).

  Below a desktop, which panel shows lasts for the visit: the stored `design-harness.panels` keeps what the desktop layout had, and only a handle's resize on a tablet writes a width to it. Both panels stay mounted at every width, so a hidden chat keeps its turn and hidden checks keep core's report.
- **Canvas:** the frames as artboards on a dotted board, one row per scenario, named the way a designer names a screen, by page and state ("Booking, room held", with the scenario's own name, "Lantern held", beside it), and one artboard per view ("Desktop 1280 × 900"), light views on one line and dark views on the next, each a live render scaled to fit. A badge shows only while a frame measures or when it failed. Zoom is Fit, 25, 50, 75 or 100%, with zoom out and in buttons. The open button on an artboard shows it at full size, in place. A **Lens** beside zoom draws tap targets or the first view over every artboard, and the summary ("4 scenarios · 4 views") opens the coverage grid ([Visual checks](#visual-checks)).
- **Checks:** a summary first ("Everything follows the project's rules", or "3 things to fix"), then one card per failing rule: the rule in plain words (its description, with the project's caps written as their values), core's message for the place shown word for word, as the caption of a figure of what the rule measured when the rule is about something words cannot show ([Visual checks](#visual-checks)) and alone when it is not, every place it was found by scenario and view or by file and line, **Show me** (the outline in its frame, with the camera moved to it, or its line in the code) and **Ask the agent to fix** (a message put in the chat, to edit and send), with the rule's id and type and every finding as core wrote it under Details. Every rule in force, in core's order with its status and findings, and core's report as JSON, sit under one more Details. A finding inside a spec layout instance opens the layout's element, with a button for each layout use above the code. Selecting a finding about elements in the source (core's `targets`, such as both primary actions of a page with two, or an element inside a layout instance) outlines each of them in every frame that draws them, and says under the finding (on its card, and in the Details list) where it is outlined and in which scenarios it is not drawn ([Element tags](#element-tags)); **Show in code** beside it opens its file at its line. A finding about a whole page has nothing to outline and opens its code at once. A finding inside a spec layout instance opens the layout's element, with a button for each layout use above the code, so the page's use (or, for an element passed into a slot, where the layout places it) is one click away. The report is also there as JSON.
- **Code:** a tab behind the checks: each prototype file and `manifest.json` in a plain editor. An edit is a new revision 300 ms after typing stops: the frames re-render and the checks run again. Edits are saved in the browser.
- **Variants:** a spec prototype's variants side by side with the page as it is, each measured in frames with core's report under it, and the slot-by-slot pick ([Variants](#variants)).
- **Project:** for a designer first, and read-only but for what starts a proposal: what a prototype can use, the rules in force in plain words (each opens to its id, type and data, and offers **Change this rule…** and **Remove this rule…**, [Removing or changing a rule](#removing-or-changing-a-rule)), the tasks and limits the rules read, the proposals, and every adopted proposal's examples re-run on demand; the library's role mapping and the views are under Technical details. For a spec prototype it starts with the prototype's layouts: each drawn alone with its examples in a frame of its own (core's `layoutPreview`), where the prototype draws it, and its parameters (type in core's words, required or not, default or example, description) under a disclosure.
- **Proposals:** every proposal, and each one's review page, where you approve, decline, send back or adopt it ([Reviewing a proposal](#reviewing-a-proposal)).
- **Agent:** the chat (below). Add a key, then describe a change, or start from a suggestion. Each tool call reads as one line in plain words ("Changed the booking page") that opens to its tool, input and result; the checks the app ran after a change read the same way ("Checked the rules: all good"); each reply's thinking, tokens and approximate cost are under its Details, beside **Undo this turn**. **Stop** stops it at any time.

Nothing in the app decides pass or fail. It renders frames, collects what they painted, and hands both the prototype and the snapshots to `checkPrototype`. The report it shows is core's.

## Spec prototypes

The app makes and edits spec prototypes only. The seed holds Nook's booking prototype as json-render specs ("Booking", id `booking-spec`), and New prototype makes a spec. A spec prototype's frames load React, the library, the page kit, `@json-render/react` (0.23.1, pinned in `JSON_RENDER`) and the spec renderer (`src/frame/spec.tsx`), and get each page as data from core's `resolvePageSpec`, with every layout instance already expanded; no prototype code exists to load. The spec renderer builds a json-render registry over the library that gives each part only the props core's catalog lists. A part that throws while it renders fails its frame with the part's name ("NumberInput could not render: ..."), rather than being drawn as nothing by json-render's own boundary and measured as missing.

Its agent writes specs. The request carries the spec system prompt and, as a second cached system block, the catalog's instructions, which `spec-prompt.ts` writes from core's catalog: the spec format core accepts, layouts with parameters (core's own format: `params`, `$param`, `$scopedId` and instances), and each part with its props, with nothing json-render teaches that core refuses. For Nook that block is 9,471 characters, and the system prompt 2,373; json-render's `catalog.prompt()`, which the trial used, was 25,576. The prototype's own layouts are not in the prompt, since they change as the agent works: it reads them with `list_layouts`. Its edit tools (the agent has no tool that writes code):

| Tool | Input | What it does |
| --- | --- | --- |
| `write_spec` | `path`, `spec` | Creates or replaces a spec file, one element per line. |
| `patch_spec` | `path`, `patches` (JSON Patch, one operation per line) | Applies the operations with json-render's patch code, after checking each target exists. While it streams, the canvas draws the draft in place. |
| `list_layouts` | none | The prototype's layouts: id, file, whether the inventory has it, each parameter (type, in words, required or not, default, example, description), and where it is drawn (core's `specLayouts`). |
| `insert_layout` | `path`, `into` (`element`, `slot` on a Page, `index`), `key`, `layout`, `params`, `slots` | Draws a new instance of a layout in a Page's slot or a part's children. |
| `set_layout_params` | `path`, `key`, `set`, `remove`, `slots` | Changes an instance's parameters and fills its slots anew. |
| `propose_variants` | `page`, `variants` (2 to 4, each `note` and `spec`), `like` | Keeps whole pages beside the prototype as variants of one page, each checked by core's `checkVariant` first: if any has an issue, none is kept. Returns each one's id and core's checks of it without frames. |
| `revise_variant` | `id`, `spec`, `note` | Replaces one variant's spec, checked the same way, keeping its id. |
| `list_variants` | none | The variants with their checks, and the picks the person applied. |

The edit tools are checked by core before they apply, with the catalog and each layout's parameters: a change with any issue is refused whole, in core's words, and nothing changes. A new layout file is judged as a layout until `set_manifest` registers it. A layout the inventory lacks is a proposal (`add-layout`, a rule that governs it, and examples whose files hold the layout, its manifest entry and a page that draws it), drafted with `draft_proposal` as any other. [docs/trials/json-render.md](../../docs/trials/json-render.md) has the trial's details, sizes and gaps, and what changed after it.

A project stored before spec prototypes has no `library.parts`. On load the app adds the description it ships for exactly that library version (`src/store/migrate.ts`; today Todae 0.10.1 and 0.11.3) and says so, or says plainly that no prototype can be made or edited in that project when it has none, and its spec prototypes cannot be checked. Every version it accepts is also served, so a project it keeps described also renders ([Library versions](#library-versions)).

## TSX prototypes, notice only

The app went spec-only on 2026-11-19, and core stopped reading TSX the same day ([docs/trials/json-render.md](../../docs/trials/json-render.md) says why). Nothing makes a TSX prototype any more: not New prototype, the seed, the wizard, the agent or the code view's manifest (a manifest edit that sets another `format` is refused, and one that leaves it out keeps the spec). A TSX prototype from an older store or an imported project file is kept, not converted, and not lost, but nothing renders, checks or changes it:

- **It loads and shows.** Core's `parsePrototype` refuses it and hands it back as it was stored (`format: "tsx"`, or none, which meant TSX); the store and the project file keep it as such (`StoredPrototype` in `src/store/project-file.ts`). The prototype picker lists it as "Booking (TSX, read-only)", and the header carries a "TSX, read-only" badge.
- **A notice in place of the board** says "TSX prototypes are no longer edited or checked here" and offers **Export code** (its files as they are, in a runnable React project whose README says nothing checked them) and **Start a spec version**, which makes a new, empty spec prototype in the same project, "<name> (spec)", and opens it for the agent to build. The canvas draws no frame for it, and the check session holds no revision for it (`Session.clear`): no frame document exists, no check runs, and the header says "Not checked".
- **Its files, read-only.** The code view shows every file and the manifest as stored, and takes no edit. The Checks tab says no checks run.
- **Nothing changes it.** The chat takes no message (the box is disabled and says why; the controller refuses a turn before any request, and every tool refuses while one is open, through the agent host's `tsx()`). Pin mode is refused with a notice, and its stored notes are listed as they were, each marked moved or gone where it was anchored to a place in a TSX file. The Variants view says it takes no variants or picks, and an earlier agent turn on it cannot be undone. A proposal's impact and a library move's dry run leave it out: core checks no TSX. Proposals and library moves are the project's, and work as before.

What a spec cannot render yet stays unavailable for now: `Toast.Region` and the date inputs whose values are `Temporal` objects (the catalog leaves them out and says why).

A project config stored or imported with rules only TSX had (`no-ambient-globals`, `no-inline-styles`, `imports-from-library`, or any rule of type `isolation` or `style-props` or membership of `imports`) loads without them: `withoutTsxRules` in `src/store/migrate.ts` takes them out of the config before core reads it, with each proposal's added rules of those types and its examples written as TSX or flagged by one, and a notice names each thing it took out. The project is stored again without them. Without that step core would refuse the whole config.

## Variants

Ben's ask was that designers create with guardrails and iterate, and that much of the choosing be a visual pick. Variants are that pick, for spec prototypes.

- **The agent offers them.** Asked for options, it calls `propose_variants` with 2 to 4 complete pages for one page of the prototype, each built only from the catalog and the prototype's layouts, with one line on what is different. Core's `checkVariant` checks each against the catalog before any is kept. They are stored with the prototype (`variants` beside `prototype` in its IndexedDB record and in the project file), apart from its files, so the prototype does not change; they survive a reload and an export and import. The chat shows a card that opens the Variants view.
- **The board shows them side by side.** For the page being compared, the page as it is and each variant get a check session of their own (`useSessions`, as a proposal's examples do): every scenario and view rendered and measured in sandboxed frames, the scenario picked at the top shown and the rest measured out of sight, with core's whole report under each: "every rule passes", or each failing rule with its findings word for word.
- **A pick answers for its own page.** Core's `pickScope` sorts each source's measured report against the prototype's as it is: findings about the picked page (it names the page, one of its scenarios, its file, or a layout its file draws; static and rendered, every scenario and view), findings elsewhere that the change brings or changes (a flow, step-budget or whole-prototype count finding that is not in the prototype's report word for word), and findings another page already had. The first two block; the third never does, and is listed under "Already on another page" in core's words. A rule that ran on the prototype and did not run on the source blocks too. So a prototype whose rooms page fails can still take a pick on its booking page, and the same failure is there after it.
- **A variant with something to fix on the page cannot be picked.** Its radio buttons and its "Every slot from" button are disabled until its measured report is clear for the page. **Ask the agent to fix it** sends the agent a message quoting core's findings and asking for `revise_variant` with its id.
- **Pick by slot.** A table has one row per slot of the page type, and a choice per source; a slot can come from any source that is clear for the page. Core's `recombine` builds the page (keys, literal ids and disagreeing state named for their source, so nothing collides), and the combination is measured in frames of its own and checked like any page. **Apply this pick** is enabled only when the combination is clear for the page in the same sense, where it used to need the whole prototype to pass every rule, measured. It makes the combination a new revision of the prototype, records the pick (when, which source supplied each slot, each variant's note, the page's file before and after) and tells the agent in its next message. **Undo this pick** puts the page back as one more revision, for the newest pick not undone, while the page is still what the pick made.
- **Dismiss, with why.** Dismiss asks "Why not this one?", optional, and removes the variant. A note is kept in the prototype's chat record for the loop, which notices notes that repeat ([What keeps coming up](#what-keeps-coming-up)); it tells the agent nothing by itself.
- **More like this.** From a variant, a note and **Ask for more like this** send the agent a message naming the variant, its note and yours, asking for `propose_variants` with `like` set; the new variants say whose they are like.
- **The agent never picks.** No tool picks, applies or undoes (the tool names hold none of those words, which a unit test checks); `propose_variants`, `revise_variant` and `list_variants` reach the app only through the host's `variants()` and `saveVariants(variants)`, which takes a list of variants and nothing else, so no tool can record a pick or change the prototype's files; every tool's input is a closed object, so `pick` or `apply` in an input is refused; and nothing reads the chat's text for a pick. The end-to-end test "no tool call or chat message can apply a pick" scripts `pick_variant`, a `pick` field, an `apply` field and `undo_pick`, each refused, and a message asking for a pick, and finds no new revision, the page's file unchanged and no pick recorded, before and after a reload.
- **TSX prototypes:** a stored TSX prototype is notice only, and the Variants view says so: it takes no variants and no picks. Picking by slot needs each page as data, which a spec is and code is not.

Built with Todae: `Card` (each source and the combination), `Table` and `RadioGroup` (the pick), `Badge`, `Alert`, `EmptyState`, `Disclosure` (what another page already had, and the rule ids), `Field` (`Select` for page, scenario and view, `Textarea` for "more like this"), `Label`, `Stack`, `Text` and `Button`. What Todae lacked, done in `app.css`: a grid of columns that hold scaled frames, with the scenarios not shown kept laid out and measuring out of sight, and the red outline on a failing variant's card.

## Code export

**Export code** downloads the open prototype as a runnable React project, `<project>-<prototype>.zip`, built in the browser. Core writes every file (`exportReactProject`; a spec prototype is written as TSX first, a stored TSX prototype's files go in as they are and its README says nothing checked them, packages/core/README.md, Code export); `src/export/code-zip.ts` zips them under one folder with [fflate](https://github.com/101arrowz/fflate), deflated, every entry dated the export's time, so the same export is the same bytes. The README in the zip names the project, the prototype, the library and React versions, the time, core's verdict at export, and anything the export could not carry over.

```text
nook-booking-spec/
  package.json          exact @tounsoo/todae, react and react-dom from the project config; Vite, TypeScript and React's types pinned
  README.md             where it came from, and how to run it
  index.html
  vite.config.ts        aliases @design-harness/page to src/page-kit.tsx
  tsconfig.json
  src/main.tsx          the entry: a scenario switcher (?scenario=<id>) and the page shell
  src/page-kit.tsx      Slot, PageProps and the shell that lays out a page type's slots
  src/scenarios.ts      each page with its page type, and the scenarios
  src/shell.css
  src/prototype/manifest.json
  src/prototype/pages/booking.tsx, pages/rooms.tsx
  src/prototype/layouts/room-cards.tsx, room-details.tsx, select-question.tsx
```

Why fflate 0.8.3: it zips synchronously in the browser with no worker or stream plumbing, tree-shakes to what is imported (`zipSync` and `strToU8` are 9.0 kB minified, 4.4 kB gzipped, in the build), has no dependencies, and is maintained (0.8.3 was published 2026-05-16, six months before this milestone, with patch releases for its older lines in July 2026). JSZip (3.10.1, 2022, then 3.10.2 in 2026) is about ten times the size and async; client-zip (2.5.1) streams but stores without compressing, and has no reader for the tests, where fflate's `unzipSync` reads the zip back.

The end-to-end test "export code downloads a zip ..." downloads the zip from the built app, checks its files, unpacks it, builds it with Vite and typechecks it with `tsc` offline (its `node_modules` is this repository's), serves the build, and opens it in Chromium: each scenario renders, the label names its field, the bound answer changes, and nothing is logged as an error.

## Isolation

A prototype is written by an agent while the user's API key lives in the app's origin. A spec is data and runs no code of its own; what does run in a frame (the boot script, React, the library, json-render and the spec renderer) runs outside the app's origin all the same, so nothing a page draws can reach the app.

- Each frame is an `<iframe sandbox="allow-scripts" srcdoc="...">`. Without `allow-same-origin` its document has an opaque origin (`"null"`): it cannot read the app's DOM, `localStorage`, IndexedDB, cookies or location, and the app's storage is not its storage. Without the other tokens it cannot submit forms, open popups or modals, or navigate the top window.
- The frame's document carries its own Content Security Policy: `default-src 'none'`, scripts only with the document's nonce (the boot script and the import map it adds), from `blob:` (the modules it builds) and from the package source's origins, styles and fonts from inline and those origins, images only `data:` and `blob:`, and `connect-src 'none'`, so `fetch` and XHR fail. The nonce is random per document, and there is no `'unsafe-inline'` or `'unsafe-eval'` for scripts, so nothing in a frame can turn a string into code: `eval`, `new Function`, an inline `onerror` attribute and a `javascript:` URL are all refused.
- The only channel is `postMessage`. Each frame document gets a random channel id per revision. The boot script reads it and removes it from the DOM before any other module loads, so it lives on only in the boot script's closure, and a frame's first answer for its revision is its only one: a later snapshot or error on its channel is dropped. The app accepts a message only when `event.source` is the iframe that channel was issued to, the channel and generation are current, and the message has exactly the fields of its type; a snapshot must also pass core's snapshot schema and be of the frame's own scenario and view. The frame accepts a message only from its parent, on its channel, of exactly a render or highlight request's shape. The app posts to a frame with target `*` (an opaque origin cannot be named); the frame posts only to the app's origin.

The end-to-end test "a frame cannot reach the app" proves it in Chromium on the spec seed. It edits the rooms page so a part's text is markup and a script that would write into the app's DOM and storage, and finds the app untouched and the words drawn as text in every rooms frame, with no image, handler or script of theirs in the page: a spec's words are never parsed as HTML. It checks every iframe's sandbox is exactly `allow-scripts`, and then, inside each of the 16 frames in turn (each brought on screen, so it is live), runs code of its own through Playwright, which stands in for any code that could run in a frame (a library part, json-render, a renderer bug): it attempts to read `parent.document`, `parent.location`, `top.localStorage`, its own `localStorage`, `indexedDB`, `document.cookie` (each throws `SecurityError`, and `self.origin` is `"null"`), to `fetch` the app (a `TypeError`: the CSP refuses it), to run an inline `onerror` attribute and an injected `<script>` (neither runs), and `eval` and `new Function` (each throws `EvalError`), and finds no channel id left in the DOM.

Why that is enough now that a spec runs no code: the frame's defences never depended on what the page's code was. The sandbox, the opaque origin, the CSP and the channel hold for any code in the frame, and the test runs arbitrary code there to show it. Before, a prototype was code a model wrote, and core's `no-ambient-globals` rule refused source that reached for the frame or the measuring code; that rule left with TSX, since a spec gives prototype code nothing to run: the catalog lists each part's props, json-render draws text as text, and actions are only `setState`, `pushState` and `removeState` on the page's own state (custom actions and `$computed` are refused, packages/core/README.md). What a frame measures is what the spec drew.

## The frame protocol

All messages carry `protocol: "design-harness/frame@1"` and the frame's `channel`.

| Direction | `type` | Fields | When |
| --- | --- | --- | --- |
| frame → app | `ready` | | The boot script is listening. The app sends nothing before it. |
| app → frame | `render` | `generation`, `modules` (bare specifier → `{ url }` or `{ code }`), `styles` (`{ url }` or `{ css }`), `page` (`{ spec }`: core's resolved spec for the scenario, the library to draw it with, and the catalog's parts), `scenario` (`{ id, state, page }`), `pageType`, `view`, `settleMs`, `tags` (whether to find element tags; false only when the app is opened with `frame-tags=off`) | Once per frame document. |
| frame → app | `snapshot` | `generation`, `snapshot` (core's `RenderedSnapshot`), `tags` (the element tags the frame drew: at most 20,000 strings of at most 1,024 characters, empty when `tags` was false; the app keeps them sorted and once each), `places` (where each tag drew: at most 20,000 of `{ tag, rect }`, the box of one element a tagged part owns, in the page's CSS px with the page at the top, in tree order, elements with no size left out; empty or absent when `tags` was false) | The page rendered, settled and was measured. The places are beside the snapshot, never in it: no rule reads them, core never sees them, and they are what lets the app tell which part is under a point of a frame that is parked ([Pinned notes](#pinned-notes)). |
| frame → app | `error` | `generation`, `stage` (`load`, `render` or `measure`), `message` (at most 2000 characters) | The page could not be loaded, threw while rendering, or never stopped changing. |
| app → frame | `highlight` | `generation`, and either `element` (an index into the last snapshot's `elements`, or `null` to clear) or `tags` (1 to 256 element tags, each 1 to 1,024 characters), never both | A finding was selected: a rendered one by its index, one about spec elements by its targets' tags, each drawn with the same overlay. |
| frame → app | `scroll` | `generation`, `x`, `y` (where the page is scrolled to: whole CSS px from 0 to 1,000,000) | After its snapshot, whenever the page's scroll position changes, at most once every 50 ms, so a lens drawn over the artboard follows the page. It is never measured: the app accepts it only from a measured frame of the current revision, and it changes no snapshot, state or report. |
| app → frame | `redraw` | `generation`, `spec` (a spec page's payload, as `render`'s `page.spec`) | A frame draws a draft in place while the agent's patch streams, or its own spec again after: no new document, no snapshot. |

A frame document renders once. A new revision gets a new document, so no module, import map or state carries over from the last one. The one exception is `redraw`: the streaming preview of a `patch_spec` is drawn in the frames already on the board as a React update, so a streaming patch takes one revision (the patch, once it applies) instead of one per preview, and frames do not go blank. A redraw is a picture: it is never measured or checked, and the revision's report stays that of the prototype it was made for. Frames are asked to render a dozen at a time, across the board, a review page's examples and the variants alike (`render-slots.ts`): they share one thread, and a frame has a fixed time to settle, so eighty asked at once starve each other and fail to measure. A slot changes when a frame renders, never what it measures. The app waits for every frame of a revision to send a snapshot or an error, or to time out after 20 s, then runs core's checks with the snapshots it has; a scenario and view without one is core's "not measured" finding, so a frame that fails fails the rendered rules rather than passing them. Not every frame is a live document at once: see Light boards.

## Light boards

A board of frames is many documents: the seed's 16, and the Variants view of a project with four views 80, each with React, the library and the page in memory. Three things keep a board light without changing what it measures.

**Lazy, complete measuring.** A frame's viewport (`FrameViewport`) tells its session it is drawn (`Session.present`) and whether it is near the screen: on screen or within half a screen of it, by an `IntersectionObserver` on the area that scrolls it, and not hidden (a card out of sight, or the board under another view, `FramesShown`). The session gives each waiting frame a turn at a render slot, near the screen first (`PRIORITY.onScreen`, then `offScreen`, and a waiting frame moves up when it comes on screen). On its turn the frame goes live: its viewport mounts an iframe with a fresh document, which renders and is measured exactly as before, in the same viewport at the same size. Every frame drawn anywhere gets a turn, on screen or not, so no frame is skipped and the report is complete: a revision is "measured" only once every frame has answered, as before. No frame waits to be scrolled to: the ones off screen are measured in the background, after the visible ones, through the same slots. While frames measure, the Checks panel says how many have answered, how many measure now and how many wait their turn, and each waiting artboard says "Waiting to measure".

**A frame cap.** Once measured, a frame away from the screen is parked: its iframe leaves the DOM, its snapshot stays in the session, and its viewport draws what the snapshot measured (controls as boxes, text as bars in its painted colour) at the same size. A measured frame that comes near the screen is drawn again in a fresh document on a fresh channel, since a document renders once; that render takes a slot like any other, is never measured into the report (its snapshot is only compared with the first, `Session.reshownCount`), and is outlined again with the finding selected and the draft being streamed. An outline scrolls only the frame's own page to the element, never with `scrollIntoView`, which would also scroll the board across the frame's boundary: each frame drawn again would jump the board to its own outline, parking the frames the person was looking at (the end-to-end test "a frame drawn again outlines its finding without moving the board"). At most 24 frames are live across the app (`live-frames.ts`): a frame that must be measured always gets a hold, parking the frame shown longest when the budget is full, and a frame to be shown waits for room. A frame whose viewport leaves mid-measurement goes back to waiting, and one given its turn whose document never says it listens fails after the timeout, so a revision always finishes.

**Checks in a worker.** Core's engine for a session runs in one module worker for the page (`check-worker.ts`): the model, the first check, each scenario's resolved page, and the check with snapshots on the model kept for that revision. `runEngine` is the one function both the worker and the main thread run, and a report crosses back by structured clone, so it is the same, byte for byte as JSON; `?checks=main` runs it on the main thread, and so does the app when a worker cannot start or fails (each call still waiting is run there). A revision's report is null until the engine answers, a tick later.

What was measured with `e2e/board-performance.mjs` (it measures a build; `--dist` measures another, such as one from before a change), before and after, on a shared and often heavily loaded machine, so the times are rough:

| | Before | After |
| --- | --- | --- |
| Nook board, live iframes once measured (1600 × 1000 window) | 16 | 6 |
| Variants view, 4 sources and the board under it: live iframes | 96 | 6 |
| Variants view: Chromium renderers' memory | 1,103 to 1,233 MB | 751 to 799 MB |
| Nook board: Chromium renderers' memory | 248 to 297 MB | 264 to 328 MB (the worker holds a copy of core) |

The long tasks left while typing are the app's own rendering. Doing a frame's document load inside its render slot makes measuring 80 frames a little slower; the time to the first full report did not change measurably.

The end-to-end test "lazy measuring changes nothing a rule measures" records every snapshot the frames send in a tall window and a short one (which parks frames out of sight), scrolls to the last artboard and back so parked frames are drawn again, and finds every render of a frame measured the same and the report the same byte for byte; "core's checks run in a module worker" compares the worker's report with the main thread's for Nook's spec prototype and for Tally; the Variants test finds at most 24 live documents with 80 frames measured.

## Element tags

A finding about elements (core's `Finding.targets`, packages/core/README.md, The report) is outlined in every frame that draws them. For that, each frame knows which spec element each part of its page came from.

- **The tag.** One prop, `data-dh-source`, on the React element of a library part or a page kit part: the spec renderer passes each part its key in the expanded page, which carries the layout instance's scope (`details/summary` is the room details instance's summary), and each of a Page's slots `<page key>/slots/<name>`; json-render hands a part its element but not its key, so the renderer stores the key on each element first. Core reads the spec files and code export writes from them, so neither ever sees a tag.
- **Where it lands.** The frame never reads tags from the DOM. After the page settles and is measured, `frame/tags.ts` walks React's tree from the root: the outermost fiber carrying a tag owns it, and the tag's elements are the outermost DOM elements under that fiber, across portals. A part that renders one element gives that element; one that renders several gives all of them; one that renders only other parts (a provider), their outermost elements; one that renders nothing, none, so the tag is not drawn. A fiber below with the same tag (a part passing its props on to an inner part or to the DOM, as Todae's do) adds nothing. The snapshot message carries the drawn tags; an outline request is answered by walking the tree again, so a spec redraw is followed. An element that is not drawn, such as one in a closed disclosure, is outlined around its nearest drawn ancestor.
- **Matching.** A target's tag is its `key`; a target with none (an element no page draws) has no tag. `planOutline` outlines a finding in every measured frame of a scenario on the target's page (any page, for a target with no page) that drew one of its tags, and lists the scenarios that could show it and drew none, which the Checks panel says ("Not drawn in scenario lantern-booked"). A finding about several elements outlines all of them.
- **Measurement is unchanged.** The prop is a `data-` attribute where a part passes it to the DOM, which has no layout or accessibility-tree effect, and tags are found after the snapshot is taken. The end-to-end test "element tags change nothing a rule measures" renders Nook's spec prototype with tags and again with `?frame-tags=off` (no prop passed, no tags found) and gets identical snapshots in all 16 frames, the tags apart.
- **Nothing in a frame forges them in a way that matters.** A spec cannot set the tag prop: the catalog lists each part's props, and the renderer gives a part only those and its tag, which it writes last. The frame reads tags only from React's props, never from DOM attributes, so an attribute set any other way is ignored. Tags only drive outlines: core never reads them, so no tag can change a check.

## Where packages come from

```ts
interface PackageSource {
  readonly name: string;                    // "local" or "esm.sh"
  readonly origins: readonly string[];      // added to the frame's CSP
  module(specifier: string, request: { package: string; version: string }): Promise<{ url: string } | { code: string }>;
  stylesheet(path: string, request: { package: string; version: string }): Promise<{ url: string } | { css: string }>;
}
```

`resolvePackages(config.library, source)` asks it for `react`, `react/jsx-runtime` (at `library.react`), `react-dom`, `react-dom/client` (at `library.react`), the library package (at `library.version`) and each of `library.stylesheets`.

- **`localPackageSource`** (the default): React, React DOM, json-render and every component library version `package.json` lists under `designHarness.libraries` (today Todae 0.11.3 and 0.10.1 and Mantine's `@mantine/core` 9.7.4, each with the stylesheets a project may name), at the versions installed in `node_modules`, prebuilt by `npm run vendor` into one ES module per specifier. `public/vendor/manifest.json` keys each package by name and exact version, so a project's library and its stylesheet are served by what its config names, and two versions of one library can sit side by side. CommonJS packages get named exports listed from the module itself, and React stays external everywhere, so the library, React DOM and the page share one React. The app reads the files from its own origin and sends their code to the frame, which never fetches. It refuses any other package or version, naming both: "the local package source has @tounsoo/todae 0.10.1, 0.11.3, but the project asks for 0.9.0". It serves only each package's root entry, not subpaths such as `@tounsoo/todae/stack`. Serving another library offline is one line in `designHarness.libraries` and the dependency at an exact version; serving another version of one is the same, with the dependency as an npm alias ([Library versions](#library-versions)).
- **`esmShPackageSource`**: `https://esm.sh/<package>@<version>[/<subpath>]`, with `?external=react,react-dom` on everything but React, so every module imports the React the import map names; stylesheets as `https://esm.sh/<package>@<version>/<path>`. Choose it with `VITE_PACKAGE_SOURCE=esm.sh` at build time or `?packages=esm.sh` on the page; `&packages-origin=<origin>` points it at a mirror with the same URL scheme.

A project can also choose esm.sh for itself, for a version the page's source does not serve: `library.source: "esm.sh"`, set only by a person from the packages notice, kept with the project and shown above the canvas while it lasts. `sourceFor` then gives that project's frames the esm.sh source (at `&packages-origin=` when the page names a mirror), and their CSP names esm.sh's origin; every other project's frames keep a CSP with no package origin. A build with `VITE_ESM_FALLBACK=off` does not offer it, and a project set to it there loads from the page's source and says so.

What was verified: the local source, end to end, in every test. The URL path, also end to end: a test serves the vendor build from a second local origin in esm.sh's URL scheme, with CORS, and the app opened with `?packages=esm.sh&packages-origin=...` loads React, React DOM and Todae by URL into the import map, the stylesheet by `<link>`, within the frame's CSP, and the legal prototype passes every rule; another does the same for the Tally project on Mantine, and a third loads one project's unserved Todae version by URL after a person chooses esm.sh for it. What was not: esm.sh itself. This environment's network policy refuses esm.sh, jsDelivr and unpkg, so whether esm.sh serves these exact URLs, keeps React external as asked for `react-dom/client`, and serves `dist/todae.css` as CSS, is untested.

## The page kit and the default shell

The spec renderer fills a page type's slots with `Slot` from `@design-harness/page`, which the frame provides (code export writes the same kit beside the TSX it writes). `Slot` renders a `<div data-slot="name">` and takes its place from the default shell, which knows the page type from the config and nothing about the library:

- Slots keep the page type's order. A body slot is one neither chrome nor primary, as core counts them. Every slot after the last body slot is the **trail**: an action page's primary slot and its alternates.
- At 600 CSS px and wider, the page is a centred column at most 760 px wide; lead and body slots are full-width rows and the trail's slots sit side by side under the body. Narrower, every slot is a full-width row.
- A slot name the page type lacks still renders, after the known slots, outlined; core's `page-structure` rule reports it.
- The root gets the view's colour scheme as CSS `color-scheme` and, when the config names `library.schemeAttribute` (Todae's `data-appearance`), as that attribute. The shell sets a system font only at zero specificity, so a library's own root font wins.
- When the config names `library.root` (Mantine's `MantineProvider`), the page and the shell render inside that part of the library, with its literal props and the view's scheme in its `schemeProp` (`forceColorScheme`). The render request carries it as `root` (the library's module, the export, the props), and the boot script takes the component from the library module, never from the spec.

The shell needs no new config field beyond `schemeAttribute`: which slots are chrome, primary and body was already in `pageTypes`, and their order gives the lead and the trail. Chrome slots render whatever the page puts in them, its own layouts included; a prototype-wide frame around every page (a top bar) is not modelled in core yet, so the shell renders none.

## How a scenario reaches a page

A frame draws its page for one scenario: core's `resolvePageSpec` puts the scenario in the page's state at `/scenario/id` and `/scenario/state`, and the spec reads it there (`visible`, `$cond`, `$template`). That is the whole contract. Nook's booking page reads `/scenario/state` to say "Booked until 3 pm" or "Held for 10 minutes". Core reads every value the spec can take there, so everything a page shows in any state is in its model and counts, as `packages/core/README.md` explains. Code export writes the same contract as React props, `PageProps`: `scenario` and `state`.

## Rendered snapshots

Inside each frame, after the page settles, `collect.ts` reads the live DOM into core's `RenderedSnapshot`. It records, in document order, every control (native controls, links with `href`, a details element's summary, widget ARIA roles, `contenteditable`, `tabindex >= 0`), every heading (with its `aria-level` or tag level), and every element that paints text of its own.

- Names: `dom-accessibility-api`'s accessible-name computation for controls and headings; an element that only paints text is named by that text. Roles from its `getRole`.
- Visible: rendered, not `visibility: hidden` or opacity 0 up the tree, not clipped to a pixel, not inside a closed `<details>`. A visually hidden control with a visible `<label>` is measured at the label, which is what a person presses.
- Text paint: font size and weight, the colour with every ancestor's opacity multiplied in, and background colours up the tree to the first opaque one; any `oklch()` or other colour is read through a canvas. An image or gradient under the text sets `overImage`. Text in a turned-off control sets `disabled`.
- Inline: a link laid out inline with other text in its block, which WCAG 2.5.8 exempts.
- `scrollWidth` and `viewportWidth` (the root's client width, less a vertical scrollbar drawn beside the page), `scrollHeight` (the page's height, which no rule reads: it is evidence for pictures), and the root canvas colour of the used colour scheme.

Determinism: the frame waits for web fonts, image decoding and a DOM that has not changed for three checks 50 ms apart, using timers, not animation frames (a browser may throttle frames in an off-screen iframe). A page still changing after 3 s is an error, not a guess. Animations and transitions run in no time. `Date` and `Date.now()` read a fixed instant (2026-01-05 09:30 UTC) and `Math.random` is seeded. Rects are rounded to a hundredth of a pixel. The end-to-end test "the same prototype gives the same report on reload" compares core's whole report across a reload.

Against a real page, core's rendered rules needed four fixes (each with tests in core): findings now carry the element's index so they can be pointed at; text over an image or gradient is unverifiable rather than passed; text in a turned-off control is exempt from contrast; and sideways scroll is measured against the width beside a vertical scrollbar. The real render also caught a bug the hand-written snapshots hid: the legal Nook prototype's select had no accessible name, because its label named no field.

## The agent

### What a turn is

A turn is one message from the person and everything the agent does about it. The app sends the conversation to the Messages API as a streamed request; text and thinking summaries appear as they arrive, and a tool call shows as soon as it starts, with its input growing. When the reply stops for `tool_use`, the app runs the calls in order against its own state and sends the results back in the next request. After every round in which the agent changed the prototype, the app waits for the new revision to be measured by every frame, runs core's checks, and adds core's report after the tool results, so a failing check reaches the agent whether it asked or not. Then the next request goes out.

A turn ends when:

- the reply stops for any reason but `tool_use` or `pause_turn` (`end_turn` is the usual one; a text reply cut off at `max_tokens` ends with a note);
- the person presses **Stop**: the stream is aborted, a tool waiting on the checks stops waiting, every tool call of the round still gets a result (`Not run: the person stopped the agent.`), and what streamed before the stop is shown but not kept;
- 16 rounds of tool calls have run for the message (`MAX_ROUNDS`): the results go back into the history and the chat says the agent stopped; the next message carries on;
- the reply is a refusal (`stop_reason: "refusal"`): `stop_details`' category and explanation are shown, nothing of the declined reply is kept and none of its tool calls runs;
- the reply hit `max_tokens` in the middle of a tool call: nothing runs, since a cut input can parse as a valid smaller one;
- a request fails. Errors come from the SDK's typed classes: a refused key (401), a key without access (403), a rate limit (429, with `retry-after`), overload (529 or an `overloaded_error` event mid-stream), a timeout or no connection, a refused request (400), a server error. Each is shown plainly, with **Retry** where retrying can help; a retry continues the same turn from the same history. A tool input the SDK could not parse at all is requested again, at most twice in a row.

### The request

```ts
// request.ts: the base client and only the beta Messages resource
const client = new BaseAnthropic({ apiKey, dangerouslyAllowBrowser: true, logLevel: "off", maxRetries: 2 });
new Messages(client).stream({
  model, // claude-opus-5-5 (default), claude-sonnet-5-5 or claude-haiku-5-5
  max_tokens: 32000,
  system: [
    { type: "text", text: SYSTEM_PROMPT, cache_control: { type: "ephemeral" } },
    { type: "text", text: catalogPrompt, cache_control: { type: "ephemeral" } }, // spec-prompt.ts, from core's catalog
  ],
  tools, // the seventeen below and in Spec prototypes, each with eager_input_streaming: true
  tool_choice: { type: "auto" }, // forced tool choice is a 400 on these models
  thinking: { type: "adaptive", display: "summarized" },
  output_config: { effort }, // low | medium (default) | high | xhigh | max
  cache_control: { type: "ephemeral" }, // caches the conversation up to its newest block
  fallbacks: "default",
  betas: ["server-side-fallback-2026-07-01"],
  messages,
}, { signal });
```

- `dangerouslyAllowBrowser: true` does two things in the SDK (`client.ts`, 1.10.0): it skips the check that throws in a browser, and adds the header `anthropic-dangerous-direct-browser-access: true`, which the API needs to answer a browser's CORS request. The key goes in an `Authorization: Bearer` header to `https://api.anthropic.com/v1/messages`, the SDK's default base URL; the app sets no other base URL and has no setting for one. `logLevel: "off"` keeps the SDK from logging, and its logger redacts auth headers in any case.
- Thinking is adaptive, these models' default and the only kind Opus 5.5 accepts; nothing sends `disabled` or a budget. `display: "summarized"` returns readable summaries, which is also where these models put their notes between tool calls; the chat shows them under **Thinking**. Effort is set explicitly on every request, `medium` by default, Opus 5.5's own default and a good start for agentic coding.
- `fallbacks: "default"` with the `server-side-fallback-2026-07-01` beta turns on the server-side refusal fallback: a request a model declines for policy reasons is re-run in the same call on the model Anthropic recommends for that refusal category. A turn a fallback continued carries a `fallback` block, shown as a note; it is echoed back as the API requires (below). On a model without a fallback configuration the request runs on that model alone.
- The system prompt and the tools are fixed text: the same bytes in every request of every conversation, so they are the stable cached prefix, and nothing about the project is in them (the agent reads it with `read_project`). The catalog's instructions are a second cached block, which changes only when an adopted proposal changes the catalog.
- The agent writes specs only. On a stored TSX prototype the chat takes no message: the controller refuses the turn before any request (nothing is sent, and the history is unchanged), and every tool refuses a TSX prototype too.

### The history

The API history is append-only (`history.ts`): earlier turns are never rewritten or dropped, every appended message is a deep-frozen copy, and an assistant turn goes back exactly as the API returned it, thinking blocks and their signatures included. The one transformation is the API's rule for a turn that a refusal fallback continued: before the last `fallback` block only text and the `fallback` markers go back, and only the tool calls after it run. It is applied once, when the turn is appended, so every later request sends the same bytes. A note the app owes the agent, such as "the person undid your changes", goes into the next user message, before the person's text; the checks after a round go after that round's tool results. Unit tests prove each request extends the previous one exactly.

### The tools

Each tool's input is validated against the same JSON Schema it is declared with (`schema.ts`) before it runs, since with eager input streaming the API no longer validates it; input that fails gets an error result naming every problem, and nothing runs.

| Tool | Input | What it does |
| --- | --- | --- |
| `read_project` | none | The library and role mapping, inventories, rule inputs, views, every rule in force as JSON, and proposals with their status. |
| `list_files` | none | The files with their line counts, and the manifest. |
| `read_file` | `path` | One file, or `manifest.json`. |
| `address_note` | `note`, `reply` | Marks one of the person's open [pinned notes](#pinned-notes) addressed, with a short reply. It is all the agent can do to a note; the prototype is not touched. |
| `delete_file` | `path` (a `.json` spec file) | Deletes a spec file. |
| `set_manifest` | `pages`, `layouts`, `scenarios`, `flow`, and `format` (`"spec"`, optional) | Replaces the manifest; core's `parsePrototype` refuses it or it is applied. The prototype stays a spec whether or not the input says so. |
| `run_checks` | none | Core's report for the current revision, once every frame measured it. |
| `draft_proposal` | `id`, `title`, `reason`, `states`, `inventory`, `rules.add`, `rules.remove`, `examples.pass` and `examples.fail` (each `name`, `files`, `remove_files`, `manifest`; a failing one also `flagged_by`); or, only when no rule type can express the rule, `needs_rule_type` (`checks`, `why_not`, `pass` and `fail` in words) in place of rules, inventory and examples | Saves the proposal as `open` with core's `propose`, then runs core's `dryRunAdoption` against the current prototype and returns its verdict or refusal. An id that exists is refused, pointing to `revise_proposal`; a draft with neither examples nor `needs_rule_type` saves nothing. A request for a new rule type is saved open and reported as a code change the user files, never as something to fix. |
| `revise_proposal` | `id`, `note`, and any of the fields `draft_proposal` takes but `id`; each one given replaces that field whole | Revises an open proposal with core's `revise`: the status stays open, and the version it replaces is kept in its history with the note. Runs the dry run again. A proposal that is not open is refused. |

The edit tools, the layout tools and the variant tools are in [Spec prototypes](#spec-prototypes). The TSX tools `write_file` and `edit_file` are gone: a chat saved with calls to them still shows them, and a new call to either is refused as an unknown tool.

Every change goes through core's `parsePrototype` and becomes a new revision at once (no debounce), so the frames re-render and the checks run again. `run_checks` and the checks after a round come from `measure.ts`, which resolves only with a report of the app's current source for which every frame answered, using the session's revisions: a report of older source is never returned, and if the source changes while frames measure it waits for the newer revision. The agent cannot approve, decline or adopt a proposal: no tool does, no tool's input has a status field (the schemas refuse unknown fields), and nothing reads the chat's text for one. A drafted or revised proposal shows in the chat as a card that opens its review page.

The dry run the agent gets reads source only: it has no frames. A proposal that adds a rendered rule therefore cannot be proven there, and the result says so (`needsMeasurement` on the card, which stays an info card rather than a warning) instead of telling the agent to fix it; the review page measures every example before the person can adopt it.

### Proposing rules

A rule in force is removed with its id in `rules.remove`, and changed with its id there and the changed rule under the same id in `rules.add`; the prompt says so in a line, and that a limit which reads a cap moves with `set-cap`. The agent can add examples to a proposal a person opened with `revise_proposal`. It never approves, declines or adopts: no tool does.

The system prompt says how: write a rule in core's rule vocabulary, as narrowly as it holds, and prove it with a passing example and a failing one flagged by it alone; only when no rule type can express it, give `needs_rule_type` (what it checks, why no type can, examples in words), which is a request for a code change and never a check; never force a rule into a type that checks something else; and a message naming evidence that something keeps coming up asks for a rule built on that evidence.

### What keeps coming up

New checks come only through the loop: the agent proposes, the proposal's rule proves itself on its examples, and you adopt it. The app helps the loop start by noticing patterns. Detection is app code over stored history (`patterns.ts`), never a model: the same history gives the same patterns in the same order. Three signals, each with a threshold of two, because one is an event and two is a pattern:

| Signal | Read from | A pattern when |
| --- | --- | --- |
| A fixed rule | The prototype's turns: each check after a change keeps the ids of the rules it failed and could not run, and a turn keeps the rules failing when it started, when every frame had measured the prototype then | The agent fixed the same rule in 2 separate turns: the rule failed at the turn's start or at one of its checks, and passed at its last. An undone turn, or one that changed nothing, fixed nothing. |
| An asked fix | Each press of **Ask the agent to fix**, kept with the chat | It was pressed for the same rule 2 times with a message sent between; presses with no message between them are one ask. |
| Repeated notes | Notes on variants you dismissed on this prototype, and the notes of every send-back in the project | 2 notes, each from its own event, share 2 content words: lowercase words of four letters or more, a trailing "s" dropped, common words left out. A group inside a larger one is left out. |

One rule's fixes and asks are one pattern, and rules fixed in exactly the same turns are one pattern too (a second primary action breaks `one-primary-per-page`, `primary-is-rank-1` and `rank-2-secondary` at once: one mistake). When there is a pattern and the agent is idle, the chat shows it above the composer, quietly: "This keeps coming up. Ask the agent to propose a rule?", what it noticed in a line, and **The evidence** (each turn with its message and time, each press, each note and where it was written) under a disclosure. Nothing happens unless you press. **Ask the agent to propose a rule** sends the agent a message naming the rules, the turns and the notes, asking it to draft a proposal with `draft_proposal` with passing and failing examples, or `needs_rule_type` when the vocabulary cannot say it, or to say why no rule would help. **Not now** dismisses it. Either answer is kept with the chat, and keeps that pattern, and any pattern about some of its rules, quiet until it has more evidence than when you answered. Only you adopt what the agent drafts.

### Undo

The first change a turn makes records the prototype as it was before it. **Undo this turn** puts that prototype back as one new revision, for the latest turn that changed the prototype and is not undone yet, so turns undo one after another, newest first. The agent is told in its next message.

### The key

- Entered in the chat, it is held in the app's memory by `KeyVault` and used only for the `Authorization` header of requests to api.anthropic.com.
- By default it is kept for the session: a reload or a new tab asks again. **Remember on this device** also stores it in this origin's IndexedDB, in its own database `design-harness-key` (store `keys`), never in the project database. **Forget the key** deletes it from memory and the device. The settings say which of the two it is, show its first characters and last four, and say where the chat is stored.
- It is never written into a prototype, the project config, a chat record, an export, a frame's document, a log or an error message: errors pass through `redact`, which replaces the key, and anything shaped like one, before anything is shown. Frames have an opaque origin, so they cannot read the app's memory or open its databases.
- The end-to-end test "the key is in no frame, export, project storage, page storage or log" proves it in Chromium: with the key remembered and a turn done, each of the 16 frames' documents (each brought on screen in turn) and string globals hold no key and reading the parent or IndexedDB throws `SecurityError`; no frame `srcdoc` has it; the export has none; the project database (which holds the chat) has none, nor do `localStorage` and `sessionStorage`; the console never printed it; the key database has it until **Forget**, after which it is empty and a reload asks again.

### Storage

The chat of each prototype is saved in the `chats` store of `design-harness` (keyed by project and prototype; the database moved to version 2 to add it): the API history and what the chat shows per turn, with its usage, cost and the prototype before the turn for undo, the rules each check failed, and `log`, what the loop reads that is not in the turns (fix presses, dismissed variants' notes, your answers to its suggestions). A chat saved before the loop has neither, and its turns count as fixing nothing. Model and effort are in `localStorage`. An open proposal is saved in the project config, like any proposal.

### Built with Todae

The chat is Todae's `Conversation` (it follows the newest message while it streams and offers a scroll-to-latest button) and `Message` (your turns and the agent's, `streaming` while a reply arrives, actions for undo and details), put together after Todae's message-parts, tool-call, reasoning, message-actions and suggestions recipes: each tool call and check is a `Disclosure` whose summary is a plain line with a status mark, opening to a `DataList` of the tool, its input and its result in `CodeBlock`s; thinking, tokens and cost are in each reply's details; before the first message, suggestions fill the box. The composer is the composer recipe's frame, `Field.Textarea` with a `Field.Row` for Send or Stop, without mentions, which nothing here needs. The key entry is a form of `Field.TextInput`, `Checkbox`, `ErrorMessage` and `Button`, with how the key is kept under a `Disclosure`. What Todae lacked, done in `app.css` with Todae's tokens: the round status mark beside a step, a code block that wraps and caps its height rather than scrolling sideways in a narrow column, and the bordered card for a proposal or variants offered, which the loop's suggestion also uses, with Todae's `Disclosure` for its evidence and `Button`s for its two answers. `Message.Time` was not used: it takes a `Temporal.ZonedDateTime`, which the browsers here do not all have.

### Verified against a fake API only

Nothing in this repository has called the real Anthropic API, and no real key was used. `e2e/fake-anthropic.mjs` writes scripted replies in the API's server-sent-event format (message_start, content blocks with text, thinking and signature deltas, tool input as `input_json_delta` fragments, message_delta with the stop reason, `stop_details` and usage, message_stop) and error bodies. Unit tests feed it to the real SDK through a scripted `fetch`. The end-to-end tests serve it over HTTPS with a throwaway certificate and CORS, and launch Chromium with `--host-resolver-rules` mapping `api.anthropic.com` to it and no proxy, so the built app, unchanged, talks to the API's real address and only the fake answers; the tests also check what the fake received (headers, model, effort, thinking, tool choice, fallbacks, that each request extends the last). They cover: an edit whose frames and checks follow; a second primary action whose failing check reaches the agent, and a fix that passes; a proposal saved open with its dry run, surviving a reload; stopping mid-stream; an auth error and a refusal; undo; and the key's absence from frames, exports and storage. For the review: a drafted proposal opening to its page with its examples side by side and the flagged line marked; approve then adopt, after which the Checks panel runs the new rule and flags a prototype that breaks it; a refused adoption shown in core's words; a decline that needs a note; a send-back that reaches the agent, which revises the proposal (scripted), with both versions in the history; the impact list; a rendered rule adopted on measured snapshots, outlined in its frame, with the same results after a reload; tool calls and a chat message that try to change a status and change nothing; and asking the agent from a finding. For variants: a scripted agent offers three, which render side by side in measured frames with their reports; the failing one cannot be picked until the agent, asked from its card, fixes it; a pick of slots from two variants applies a revision that passes every rule and undoes; "more like this" reaches the agent naming the variant; and tool calls and a message that try to pick change nothing. For spec prototypes: the catalog's instructions and the spec tools in the request, a patch the catalog refuses, a streamed patch drawn in place, a scripted agent that lists the layouts, draws an instance of one and changes its parameters, and a new prototype's agent writing specs by default. For the loop: a scripted agent that fixes the same rules in two turns, after which the suggestion appears (not after the first), sends nothing by itself, and once accepted reaches the agent with the rules and both turns, and the agent drafts a proposal; the suggestion stays quiet after the answer and a reload; no suggestion after a single fix or turns that fix nothing; and a scripted request for a new rule type, shown on its review page as a code change with core's refusal and no Approve or Adopt, whose copied request is the text the page shows, marked in the list, and declined with a note. What only the real API can show is untested: that it accepts this exact request (the beta names, `fallbacks: "default"`, `display: "summarized"`, the tool schemas), real streaming timing, real refusal and fallback behaviour, prompt caching hit rates, and the costs shown.

## New project

**New project**, beside New prototype, opens a wizard that takes the whole page. A designer names a product, connects the component library it is built with, confirms by eye which of the library's parts play each role the rules read, and gets a project with a starter prototype on the board that passes every rule. Cancel leaves everything as it was. Nothing is saved until Create.

### How the browser gets a library's description

The app is a static site, and two things about a library cannot be made in a browser on one:

- **Its description.** Core's `describe-library.mjs` reads a package's TypeScript declarations with the TypeScript compiler, after installing that exact version with npm so its dependencies and React's types resolve the same on every run.
- **Its code.** A frame loads only what the deployment's package source serves, and its Content Security Policy refuses everything else.

So the first version does what works with no server, and says so:

1. **Pick a library the deployment ships.** `src/libraries/registry.ts` lists each library that is both described (`packages/core/libraries/<name>.json`) and vendored (`designHarness.libraries` in `package.json`): today Todae 0.11.3 and Mantine's `@mantine/core` 9.7.4. (Todae 0.10.1 is described and served too, for projects made before the upgrade, but New project does not offer it.) Each entry carries what a description cannot say: its stylesheets, the React it renders with, the attribute or root part that switches light and dark, a rule of its own, and props its starter needs to pass the rules (Mantine's buttons are violet, since its default blue under white text is 3.5:1). Mantine's 3 MB description is a chunk of its own, fetched when it is picked (46 kB gzipped). `registry.test.ts` holds each entry to the description file, to `package.json` and to the version installed, and builds a project on it.
2. **Import a description file.** The JSON `describe-library.mjs` writes, validated by core's `parseLibraryDescription`. The person gives its stylesheets, and the part every page renders inside and how it switches schemes when it needs them. This covers a description made outside the deployment, but not the code: leaving the step, the app resolves the library through the package source, and when that refuses (`the local package source has no @acme/ui`) the wizard stops there and says the deployment cannot render it. With `?packages=esm.sh` the source resolves any published package, so an imported description goes on; that path is untested against esm.sh itself ([Where packages come from](#where-packages-come-from)).
3. **Describing in the browser was left out.** It would mean shipping the TypeScript compiler (about 3 MB minified), fetching a package's declarations and those of everything they import from a CDN, and resolving versions without npm's `--before`, so the same package could describe differently on two days. It is neither light nor deterministic yet, and this environment cannot reach a CDN to test it.

Adding a library is a change to the repository: the dependency at an exact version and a line in `designHarness.libraries`, a description written by `describe-library.mjs`, and an entry in the registry. A designer asks for one from the wizard, and a workflow makes that change.

### Requesting a library

Under "Use a library that is not listed", the library step takes a package name, an exact version and the library's stylesheets, and checks them as the workflow will (`scripts/library-request-input.mjs`, shared by both): an npm package name, lowercase, never starting with `-`, `.` or `_`, with no `..` and nothing a branch name cannot hold; one exact version, with a plain word for a range (`^1.2.0`), a tag (`latest`), a leading `v` or build metadata; `.css` paths inside the package, at most five, with no `./`, `..`, leading `/` or backslash. Each refusal shows under its field. A library the list already has is picked there instead. **Request on GitHub** opens the repository's issue form (`.github/ISSUE_TEMPLATE/library-request.yml`) in a new tab, filled in by its query parameters, for the person to submit; Enter in a field does the same, since the fields sit inside the step's form. The app holds no GitHub token and files nothing itself.

A request this browser sent shows as **pending**, kept in localStorage (`design-harness.library-requests`, every entry checked again as it is read): with no token the app cannot see how it went, so each links to the issue search that finds it, the pull requests from its branch, and the filled-in form again, and can be forgotten. It goes away once the deployment lists the library.

The issue starts the library request workflow (`.github/workflows/library-request.yml`, its logic in `scripts/library-request.mjs`, unit-tested in `src/libraries/request.test.ts`):

1. **parse** (read access): runs on issues labelled `library-request`, opened or with their fields edited, while open. It reads the fields under their headings and checks them again, and stops, saying why on the issue, when the request is written wrong, names React or another package the app serves itself, is already served, or already has a pull request or branch.
2. **build** (read access, one run at a time per package and version): asks npm for the exact version and stops when it is not there, ships no TypeScript types of its own, asks for a React the frames do not have, or is deprecated; describes it with `describe-library.mjs` from a copy installed alone with npm's `--before` one second after it was published; stops when core cannot draft a part for every role or build a project whose starter follows the rules; then adds the dependency (under the alias `<package>-<version>` when another version is served), the version and its stylesheets under `designHarness.libraries`, and a registry entry, and runs `npm install --ignore-scripts`, checks the stylesheets are in the package, and runs `npm run check`, `npm run build` and the end-to-end test `a requested library` (`E2E_LIBRARY` names it: New project draws every role and its starter passes every rule, measured). A new version of a listed library copies that entry's `setup` and `notes`; a new package gets the frames' React and its stylesheets and nothing else, so one that switches light and dark by an attribute or a root part fails the dark views until a person sets that up.
3. **publish** (contents, pull requests and issues: write): on a clean checkout, makes the `package.json` and registry edits again from the request, takes only the description and the lockfile from the build, refuses a change to any other file, pushes `library-request/<package>-<version>`, opens a pull request that closes the issue (what changed, the describer's draft with confidences, style-prop exclusions, parts count, a checklist of what a person must check, what ran), and comments the link on the issue.
4. **report**: when parse, build or publish stopped, comments the reason on the issue, with the end of the failing command's output in a fence it cannot close.

The issue's text and the package are both untrusted. The text reaches the script only through the event file, never the workflow's expressions or a shell, and every command takes an argument list. Every install skips install scripts, so nothing from the package runs in Node; only the end-to-end test runs it, in a sandboxed frame, in a job that cannot write. A pull request opened with the workflow's token starts no workflows, so CI has not run on it: the workflow runs the same checks first, and the pull request says so.

### The steps

Built after Todae's wizard recipe: a `Steps` list for where the person is, a `Form` per step whose Next is its submit button, and focus moved to each step's heading. One thing differs from the recipe, which keeps every step mounted: only the current step is mounted, because a step's previews are live frames and a frame in a hidden form has no viewport to render in. The answers live in the wizard, so Back keeps them.

1. **Name the product.** The id core will give it shows under the field (`projectId`: "Ledger" is `ledger`, a second one `ledger-2`). An aside adds core's Tally example, or opens it when the browser already has it.
2. **Pick the library.** The shipped libraries, or a description file. What the project will say about the library is shown before going on: package, exact version, parts described, stylesheet, React, and each note of the registry entry.
3. **Confirm the roles.** One card per role (action, primary action, secondary action, disclosure, disclosure summary, question):
   - the drafted parts **drawn live** in a frame sandboxed exactly as the board's are (`allow-scripts` alone, the same document, CSP and protocol), with the library's own stylesheet and inside its root part, in the app's light or dark scheme. Core's `rolePreview` writes the one-page spec: an action as a pressable part, a primary or secondary action once per prop value and once with no prop when `whenMissing` (so the person sees what a button with no variant looks like), a disclosure with its summary, a question with its label. The frame shows as much of its view as the page fills;
   - core's confidence as a badge and its evidence, word for word;
   - **what it could be instead** (core's `roleOptions`), under "Pick another part" or "Pick other values": the parts as checkboxes, or every value of the action part's emphasis prop, with one more frame that draws all of them to pick from by eye. The preview follows what is checked.

   A drafted role counts only once **Accept** is pressed (or "Accept all as drafted"). A changed role is a correction and needs a reason, which core's `confirmRoles` refuses without; the refusal shows on the card in core's words. A role left with no part shows what core's `missingRoleEffects` says: the rules that leave the project, each by its description and id, since a config holding a rule that could never fire is refused.
4. **Confirm the style props.** The props core drafts to exclude from specs, with its evidence, as a list to accept or change (uncheck one, or add names and `*` patterns); a change needs a reason.
5. **Starting rules.** Tasks with their step budgets, the two ranked actions, and the four caps, each with a sentence on what it means and core's defaults (`defaultStarterRules`: one task in three steps, "Continue" and "Not now", one question and one disclosure a page, 24 px targets). Then the parts a prototype may use: core's `starterInventory`, changeable, with the parts the roles map to locked in. The page types and views every new project starts with are listed, not editable here.
6. **Review and create.** The project as core built it (`buildProject`), and its starter page drawn in a frame per scenario and view and measured, with core's verdict: "It follows all 32 rules", or each rule that finds something. Create is held until the frames have answered. It stores the config and the starter, opens the board on it, and says so in a notice.

### What decides

Nothing in the wizard decides what is valid. Each Next runs core's `buildProject` on the answers so far and shows the refusals that belong to that step, each beside what it is about (`wizard-model.ts`'s `routeIssue` sorts them by path); Create is reachable only with a config that came back from `buildProject`, which returns one only after `parseProjectConfig` accepts it. The starter is core's too (`starterPrototype`), returned only when `checkPrototype` finds nothing in it; when a library has no part core can tell writes a heading or text, the project is created with an empty prototype and a notice saying why. How each role was decided, reasons included, is kept in the config (`library.confirmed`) and shown under the Project view's technical details.

The header's project picker lists every project in the browser's store (it appears with the second one), and switching opens the other project in a fresh workspace. Which project was open last is kept per viewer in localStorage (`design-harness.project`) and restored on load; blocked storage only means the first project opens. ## Reviewing a proposal

The top of the review page is drawn (`src/visual/project-figures.tsx`, from `project-model.ts`, which decides nothing): where the proposal stands as a track (Drafted, Open, Approved, Adopted, or ending at Declined) with what the current step waits for; core's classification on the scale, with each change's own class and core's reason under it; under "What it changes", each component it adds or removes as a live palette tile marked New or Removed, and each cap or step budget it moves as its limit before and after in words (a length cap as squares at their actual sizes), each page type as its slot diagram; each rule it adds as a card with core's words (and the rule's glyph when it is about how the rendered page looks), and two of its examples under it, the first passing one and the first failing one the rule must flag, each in a frame of its own at one scenario and view with core's verdict and message (they are two examples, not a before and after); and the impact as a grid with a tile for every prototype in the project, a newly failing one outlined, with a miniature of its page from measured boxes when core's finding names an element to hatch on it (a finding about a line of code has nothing to mark, so no miniature). Core's words stay beside every figure, word for word. The full Examples section, Why, the states and History are as before.

The Proposals view shows every proposal as a card that leads with what it would put in the project (`ProposalPreview.tsx`, keyed by its first inventory change, else its first added rule): a new part drawn live by the project's library, a cap or a step budget as its limit before and after, in words with "stricter" or "looser" (two numbers need no picture; a length cap is two squares at their actual sizes), a new page type's slots, a new state, a rule in core's words (with its glyph when it is about how the rendered page looks). Under the lead: title, status and what it waits for, core's classification as a word (only adds, tightens, loosens or removes; the three-stop scale that places it among the others is on the review page, once), what changes in a line, its example counts, who drafted it and when, and its id. The list is filtered by status with a count on each filter, open proposals first. The header's Proposals button shows the number of open proposals as a badge, and nothing else asks for attention. A proposal opens to its review page from the list, from the chat's card, or from the Project view.

### The page

- **Header and actions.** Title, status, classification, id, who drafted it and when. The actions are a sticky bar with core's adoption dry run beside them: Approve (open), Adopt (approved), Send back to the agent (open), Decline. Each is a deliberate click; decline and send back open a note form and refuse to go on without a note. Every status change goes through core's lifecycle and is stamped with the time and `by: "you"`: there is one user, and the field is kept for accounts. A refusal is shown in core's words with its code, the example it names (a button scrolls to it), and for an earlier adopted proposal's broken example, that proposal (a button opens its page), with its findings.
- **Why.** The reason and the state notes.
- **What it changes.** The inventories and rule inputs before and after, from core's `applyProposal` on the config as it is (`src/review/diff.ts`): lists as badges, with what is added or removed marked, and changed rows (caps, tasks, page types, ranking, roles) as before and after. Each rule it adds or removes in core's `describeRule` words, its author's description under them, and its data one click away. A rule it removes reads "Removes rule `id`" over the rule in core's words. A rule it removes and adds again under its id is one changed rule: "Changes rule `id`", each limit before and after with the way it moved ("at most 1 → at most 2, looser"), the rule as it was, the rule as it would be, and its proof; it is not listed again as added or removed. Both lines come from core's classification (`ruleLines` in `src/visual/project-model.ts`), which an adopted proposal keeps, so the page reads the same once the old rule is gone from the config. The Proposals list leads a card with the same line, labels a changed rule "rule" as it labels a changed cap "cap", and counts it once ("Changes 1 rule.").
- **Examples.** Passing examples on the left, failing on the right, each a card with its frames at the chosen scenario and views (below), core's verdict as a badge ("passes", "fails for one-toast-per-page alone", "does not behave"), core's words for what happened, and the findings. On a failing example, a rendered finding is outlined in its frame with the board's own highlight (the frame's overlay), and a source finding's line is shown marked, as the code view marks it. The scenario picker opens on the scenario the first failing example is flagged in.
- **Impact on the project.** Core's adoption check against every prototype in the project, each measured: the prototypes that would newly fail, with the findings, and Open on the board, which shows the prototype and points at the finding. When the dry run refuses (an example misbehaves), the impact still comes from core's `newlyFailingOf` with the proposal applied.
- **Classification**, change by change with core's reasons, and **History**: every status change, revision and send-back, by whom and when, with its note; a revision opens to the version it replaced.

Once adopted, the page says which rules are in force and what the re-check of every prototype found; the open prototype's checks run again at once with the new rule, and the Checks panel shows a rule without a description in core's words. An adopted proposal's examples are judged with core's `rerunExamples`, on the snapshots stored at adoption.

### How examples are rendered and measured

Each example is a prototype. `useSessions` (`src/app/sessions.ts`) gives each one a check session of its own, the same `Session` the board uses, with the same frame documents, sandbox, protocol and collector: one frame per scenario and view, rendered with the proposal applied to the config (so a component or page type it adds is there). A session is keyed by a hash of everything a frame's paint depends on: the library, its version and stylesheets, the views, the page types and the example's source. When a revision changes an example, its key changes, a new session measures it from scratch and the old one is dropped, so no measurement is ever reported for content it was not taken of. Frames of other scenarios stay laid out, hidden, so every scenario is measured, not only the one shown. The project's other prototypes are measured the same way for the impact; the open prototype's snapshots are the board's.

The verdicts wait for a complete measurement: until every frame of every example has answered with a snapshot, the cards say how many have, and Adopt is disabled with the reason beside it. A frame that fails or times out leaves its example "not measured", and core's `withExampleSnapshots` would refuse the partial measurement anyway, so adoption never runs on one.

### Where the adoption snapshots are stored

With the proposal, in the project config: Adopt calls core's `withExampleSnapshots` with the measurement, which stores each example's snapshots on the example (`examples.pass[i].snapshots`, `examples.fail[i].snapshots`, core's existing optional field), and then core's `adopt` on that config, which keeps them on the adopted proposal. The config is saved to IndexedDB and goes into the export. Re-running the examples later, on the Project view or after a reload, reads those snapshots: nothing is rendered again, and the end-to-end test checks that no example frame exists while it re-runs and that the results equal the ones at adoption.

### Send back, and the agent's revision

Send back records the note in the proposal's history (core's `sendBack`) and sends it as the person's next chat message, naming the proposal and asking for `revise_proposal`. It needs a key and an idle agent; the page says which is missing. The agent revises with `revise_proposal`, which keeps the history; the chat shows a "Proposal revised" card, the open review page follows the new version, and its examples are measured again.

### Removing or changing a rule

A rule changes only through a proposal a person reviews, approves and adopts. The agent drafts one with `draft_proposal`; a person starts one from the rule's card in the Project view. Nothing in the app edits `config.rules`: both flows end in core's `propose`, stamped `by: "you"`, and open the proposal's review page, where Approve and Adopt work as for any proposal. `src/review/rule-change.ts` is the flows' model, pure and unit-tested; `src/app/RuleChange.tsx` is the dialog; `src/app/project-measure.tsx` measures every prototype in the project in frames while a flow is open (the hook the review page's impact uses).

- **Remove this rule…** shows the rule in the card's sentence and in core's words, asks why (required), and says what it would do: core's `proposalImpact` on every prototype, measured, as one line each (how many findings it has from this rule now, and whether it would stop failing), and the failing examples adopted proposals keep that the removal retires. A proposal that already waits on the rule is named, with a button to it, here and on the card.
- **Change this rule…** edits the rule's numeric limits in place: a count's or a slot's `min` and `max`, a nesting `depth`, a target's `minPx` (core's `ruleBounds`). A step button, an arrow key, or leaving the field commits a number; under it the limit reads before and after in core's words with "stricter" or "looser", the whole rule as it is and as it would be, and core's class for the draft with its reason. The proposal removes the rule and adds it again under its id with the new number. The rule's own sentence usually names the old limit, so it is not carried over unless the person writes one; left empty, the card leads with core's words.
- **A limit that reads a cap** says so, with the cap's value and the other rules that read it. Changing it moves the cap with `set-cap` and leaves the rule alone, and the impact counts the findings of every reader.
- **Anything else** (what the rule selects, where it looks, its type) is "Ask the agent to draft this change": the person's words and the rule in core's words are put in the chat for them to edit and send. A rule with no number offers only this.
- **Examples.** A removal needs none: core adopts a proposal that only removes rules on no examples (`onlyRemovesRules`), so the remove dialog takes none and says why, and its impact list is what shows what it does. Core adopts any other proposal only with a passing and a failing example, and a changed rule needs a failing example it flags alone (a stricter limit: a prototype the new limit flags). The flow takes them from what the project has and writes none: `chooseExamples` reads every prototype with the draft applied, on its measured snapshots, as `adopt` will, and picks one that passes every rule (one the change clears first) and one that the needed rule flags and no other does; the examples adopted proposals keep come after the project's prototypes. The dialog lists what it picked and from where. What the project lacks is named in words, and **Open it and ask the agent for examples** opens the proposal and puts a message in the chat asking for them with `revise_proposal`; until it has them, the review page shows core's `missing-examples` or `unproven-rule` refusal.
- **What core would refuse.** A change that breaks an example an adopted proposal keeps (loosening a rule past its own failing example, or tightening it past a kept passing one) is shown before the proposal is opened, with the example and core's words: core holds earlier examples to a replaced rule of the same id, and only a removal retires them.

### Asking the agent to propose

A failing check whose finding is about something outside the inventories (a membership rule over components, page types, layouts or flow states) offers "Ask the agent to propose this" in the Checks panel, when a key is set. It puts a message into the chat's box, quoting core's finding and where it is, for the person to edit and send; it never sends on its own.

### A request for a new rule type

A proposal with `needsRuleType` (core's [Proposals](../../packages/core/README.md#proposals)) opens to a page of its own. First, plainly: **Needs a new rule type: this is a code change**, core's own refusal to approve it word for word, and **Copy the request to file**, which copies the issue core's `ruleTypeIssue` writes (a `#` title, then the Markdown body) and says it did, or why not. There is no Approve or Adopt: core refuses both. Send back and Decline work as on any proposal; once filed, decline it with a note saying where. Then what the rule should check, why the vocabulary cannot express it, its examples in words (must pass beside must fail, with any snippet), the reason, the request as it is copied in a read-only field, and the history. The Proposals list marks it "needs a new rule type" where other proposals show their class, and counts its examples "in words". In the chat its card reads "Request for a new rule type drafted" and opens the page.

### Built with Todae

The review uses Todae's `Card` (actions, example cards, impact), `Table` (the list, rows of the diff, the classification, the re-run examples), `ToggleGroup` (filters), `Badge`, `Steps` (the history), `Disclosure` (rule data, earlier versions), `Alert` (refusals, the adopted notice), `DataList`, `EmptyState`, `Field` (`Textarea` for notes and the read-only marked excerpt, `Select` for scenario and view), `ErrorMessage`, `Label`, `Code`, `Stack`, `Text` and `Button`. What Todae lacked, done in `app.css`: two columns of example cards that hold scaled frames, a before-and-after layout for the diff, a sticky action bar, and a read-only code excerpt sized to its lines. `ToggleGroup` wraps each text child of an item in its own span, which splits the button's accessible name, so each filter label is one string.

## Visual checks

Where a picture shows something the words beside it cannot (a size, the colours themselves, a place on the page, a gap, an order, a route), the app shows the check as a picture as well as words. Where the words say it whole (a count against a limit, a name missing from a list), there is no picture: a generic shape beside the sentence would only repeat it. Two things hold for every picture:

- **The app draws; core decides.** A picture is a pure function of core's evidence and facts ([core's README](../../packages/core/README.md#evidence)). The app never works a verdict out for itself: the neighbour a small control meets, a count and its cap, a route and its budget all arrive as numbers on the finding.
- **A picture never replaces the words.** Core's message is on every card word for word: as the figure's caption and its text alternative, or alone where there is no figure. The agent gets core's text only (`describeMeasured`), never a picture or the evidence.

A failure is never colour alone: it is hatched, or solid where passing things are dashed, it carries a mark (✕, a diamond, a square number), and it is said in words beside the picture. Every drawing is either hidden from assistive technology with the same facts in words next to it, or has a role and a name.

### Evidence figures

Each check card (`ChecksPanel`) and each failing example on a proposal's review page shows its finding's figure, between the rule in plain words and core's message, when the finding's evidence kind draws one. A figure is a schematic drawn from measured boxes, never the page's pixels, and says so.

| Evidence kind | Figure |
| --- | --- |
| `box-with-neighbour` | The control at a fixed scale ("Shown at 4×"), its measured width and height as dimension lines, the dashed circle the spacing exception gives it, and the neighbour that circle meets, hatched where it reaches it |
| `colour-pair` | The real text in its measured colours, one row for each colour scheme the rule's findings cover in that scenario, each with its ratio and its pair as hex, and under them what the text needs ("16 px: needs 4.5:1"). The colours are the picture; the ratios are numbers, so no scale repeats them |
| `sequence-gap` | The heading outline as an ordered list, indented by level, with a dashed empty row for each level skipped and the heading out of order flagged in words |
| `count-vs-cap` | None. Core's message says the count and the limit and names each element counted ("has 2 primary actions, more than 1: …"), and the elements are outlined in their frames |
| `region-line` | A close-up of where the first view ends, with the action under the line and the part below it hatched; or the first view in miniature with a hatched strip as wide as the page runs past its edge |
| `route-vs-budget` | The flow map (below) |
| `coverage` | None. The message names the state with no scenario; the coverage grid (below) shows every state against every view |

There is **one entry per evidence kind, never per rule** (`FIGURES` in [`src/visual/figures.tsx`](src/visual/figures.tsx)), and an entry either draws (`shows`, `Figure`) or says in words why its message stands alone (`wordsOnly`). So a rule a proposal adds in the existing vocabulary is shown the day it is adopted: the review page of a "one Toast per page" proposal shows its failing example with core's message, "Page \"booking\" has 2 Toast.Root, more than 1: …", and both toasts outlined in the frame. A finding with no evidence, or with evidence of a kind that draws nothing, has no figure and nothing in its place: the card leads with core's words. "Show me" and the outline in the frame show where an element is, on the page itself.

**To show a new evidence kind**, after core has it ([core's steps](../../packages/core/README.md#evidence)): add its entry to `FIGURES`. Decide first whether a picture would show what the message cannot; if it would, add the figure with its geometry as a pure function in `geometry.ts` and a test beside it, and if not, write the reason as `wordsOnly`. The registry's type lists every kind, so the app does not compile until the kind has decided, and [`figures.test.ts`](src/visual/figures.test.ts) fails when a kind core declares has no entry, when a figure drops core's message, when a kind with no figure puts anything above the message, or when a drawing is neither hidden nor named. A new rule *type* that reuses a kind needs nothing here at all.

### "Show me" moves the camera

Selecting a finding scrolls the board to its artboard. When the element it points at would be too small to see at the board's zoom (its longer side under 16 px on screen, or a sliver under 4 px: `visual/camera.ts`), the artboard opens at full size with the element in view, a status line says so to a screen reader, and **Back to board** returns. Putting the finding down closes an artboard the camera opened. Zooming or scrolling afterwards is the person's own: only a new finding moves the camera.

### Lenses

A **Lens** control beside zoom (Todae's `ToggleGroup`, also in the canvas-only bar) draws one family of rules over every artboard at once, passing parts included, so a designer can look before anything fails. One lens at a time; pressing the pressed one turns it off.

- **Tap targets:** every control's hit area as a quiet dashed box. A control core fails gets a solid box, a hatched circle of the minimum's diameter, and its name and size beside the cluster it is in. Under the artboard: "2 of 6 controls are under 24 px and too close to another."
- **First view:** a labelled line where the first view ends, and under the artboard a ghost of what was measured below it, as boxes, with the named action hatched; the view's edge, with a hatched strip beside the artboard and its width in px when the page runs past it, and what crosses the edge outlined. Under the artboard: "\"Book room\" ends 81 px below the first view. The page is 96 px wider than the view."

A lens is drawn by the app, outside the frame (`visual/LensLayer.tsx`), from `viewFacts` for the frame's snapshot. So its lines and labels keep their size at any zoom, and nothing that is measured changes: the end-to-end test "lenses change nothing a rule measures" compares core's whole report, evidence included, with each lens on and off. It is drawn only over a measured frame; while a revision measures there is nothing true to draw. What belongs to the page moves with the page when the frame is scrolled, which the frame reports (`scroll`, in [The frame protocol](#the-frame-protocol)); the view's edge and the ghost stay put. The ghost never runs further than one more view; the words say how far the page runs. Labels are placed in a fixed order and stepped clear of each other (`placeLens`), so the same drawing at the same zoom always looks the same.

An artboard is the prototype's page in its view's own scheme, so a lens's ink cannot follow the app's theme: it comes from the `harness.annotation` tokens, fixed for a light page and for a dark one, each stroke with a halo so it reads on whatever the page paints there.

**Performance.** A lens is one small SVG per artboard, built from shapes that are memoised per snapshot, lens and zoom; a scroll inside a frame re-renders only that artboard's layer. Measured in Chromium on the build with `e2e/lens-performance.mjs`, on a failing Nook board at 16 frames (the seed) and at 40 (the same project with 10 views): a lens is on 29 to 36 ms after the click, painted, at both sizes (560 SVG nodes for tap targets at 16 frames, 1,400 at 40); scrolling the whole board over two seconds holds 16.7 ms a frame, median and worst, with either lens on as with none, and no frame over 50 ms. So every artboard's layer is drawn, in view or not: nothing needed to be left out.

### The coverage grid and the flow map

The two flow rules have no element to point at, so they get pictures of their own, from `flowFacts`.

- **Coverage grid:** the canvas summary ("4 scenarios · 4 views") opens a table of flow states against views. Each cell says "Passes", "2 to fix", "Measuring" or why the frame failed, and is a button that scrolls the board to that artboard and moves focus to it. A flow state no scenario shows is a dashed row, "Never drawn: add a scenario". A cell counts core's findings that name its artboard, its scenario or its page; a finding with no place is on no cell.
- **Flow map:** each task's routes, on the step-budget rule's card when it fails, under that rule in Details when it passes, and in the Project view under the tasks. The longest route runs down a spine with its steps numbered; a step past the budget is a square, hatched number below a "budget 3" line; every other transition is dashed; a state with no scenario is dashed too. Under the map the count is a line of words ("4 steps on the longest route, budget 3"), and the same route is an ordered list, which is what a screen reader reads, and each state in it goes to its artboard. The layout is deterministic (`visual/flow-map.ts`); a flow of more than 10 states is the list alone.

### Built with Todae

`ToggleGroup` in the canvas `Toolbar` for the lens; `Popover` with `usePopover` and `Table` for the coverage grid; `Card`, `Disclosure`, `Text`, `Button` and `VisuallyHidden` as elsewhere. What Todae lacks, done as SVG and CSS on its tokens in `app.css` and listed for Todae:

- No annotation parts: a hatch fill, a dimension line, a callout label, a guide line. Every figure and lens is made of these.
- No diagram or graph part, for the flow map.
- No colour swatch or colour-pair sample outside `ColorPicker`.
- `Meter` is the native element: it has no threshold mark and cannot place two values on one scale, so a count against a limit is written as words.
- No tokens for ink drawn over content of another scheme. The harness adds `harness.annotation` (`on-light` and `on-dark` ink, fail and halo; stroke, dash, hatch and label sizes) and `harness.figure` (sizes) in `tokens/harness.json`.
- No pattern token: the hatch is an SVG pattern and a CSS gradient written from the annotation tokens.
- `Button` has no size for sitting inside small text: a state in the flow's list sets `--todae-button-font-size` on itself.

## Pinned notes

A designer leaves feedback on a spot of a frame, and the agent gets it as a finding to fix. The code is `src/pins/`: `model.ts` (the pins, their history and the only operations on them), `anchor.ts` (where a pin is, and where it is after a change), `describe.ts` (pins in words), `pick.ts` (a variant's notes when a pick is applied or undone), `PinLayer.tsx` (the markers and cards over an artboard) and `PinNotes.tsx` ("Your notes").

**A pin is never a check.** Pins are kept beside the prototype (`PrototypeRecord.pins`), outside the `Prototype` core checks, and nothing in `packages/core` knows them. A pin starts no revision and changes no report, verdict, count or badge. They show apart from core's findings: their own section under the checks ("Your notes"), their own words ("note", "open", "addressed by the agent", "closed"), their own mark (a violet numbered drop, on the `harness.pin` and `harness.note` tokens, a colour no check uses). The end-to-end test compares core's report byte for byte before and after.

**Pinning.** "Pin a note" in the board's toolbar, beside the lenses (Ctrl+Alt+N, ⌥⌘N on a Mac), puts a surface over every measured artboard; Escape closes an open card first, then leaves the mode, then leaves canvas only. The click is taken by the app, outside the frame: the frame never hears it, its sandbox and CSP are as they were, and nothing is asked of it. The click's offset on the overlay becomes a point of the page by the artboard's zoom and the frame's scroll (`toPage`: `offset / scale + session.scrollOf(frame)`). Without a pointer, each artboard's head has "Pin a note … pick an element from a list" while the mode is on: the list is the frame's visible, named elements from its snapshot, and the note goes on the middle of the one picked. A pin's marker is a button; its card is a Todae `Popover` (the note, its state, the agent's reply, Edit, Close note, Reopen, its history). Nothing here calls `scrollIntoView` or focuses with a scroll: only the app's camera moves the board ("Show me" in Your notes uses the same camera a finding does, and opens the pin's card).

**The anchor.** A pin holds its scenario and view, the point in the page's CSS px, the revision it was made on and the one it was last found on (a fingerprint of the prototype's content), and what was under the click: `source`, the innermost tagged part there (its [element tag](#element-tags), the spec element's key, and its box), and `label`, the measured element there (role, accessible name, HTML tag, box; the control rather than the text inside it), each with where in its box the point is as a fraction. Both come from what the frame measured (the snapshot's boxes and the snapshot message's `places`), so a pin is made, drawn and re-anchored the same on a live frame and on a parked one.

**Across revisions.** Each time frames are measured for the open prototype, every pin on them is placed again (`reanchor`): by its tag, believed while what the tag draws there is still the element the pin named; otherwise by that name, adopting its new tag (the spec was rewritten and the element keyed anew); and when the name is nowhere, by the tag alone (renamed where it stands), since a key names its element whatever is around it. Everything that decides is in the pin and in the measurement, so the same decision is made in the session the pin was made in, after a reload, and after an export and import. The point keeps its place within the element's box. A pin stored on a TSX prototype was anchored to a place in a file, which nothing draws any more: it loads with its note, point, label and history, without that place, and marked lost. When nothing finds it the pin is `lost`: it stays at its last position, drawn dashed with a question mark, and says "Moved or gone" on its card and in the list. A lost pin is found again only by its element's name. A pin whose scenario or view left the prototype stays in the list, saying so. No pin is ever dropped.

**The agent.** The open pins ride with each message the person sends, as a text block before their words (`describePins`), each in the shape of core's findings in the checks text: `- note 3: "…" [spec element "hold", scenario lantern-open, view desktop]`, then `on:` the element (role and name, or "moved or gone") and `where:` the part of the view, the point, how far into its element, and what is drawn nearest. The system prompt says what they are: feedback, never checks. The agent has one tool for them, `address_note` (`note`, `reply`, nothing else), validated like every tool: it marks an open note addressed with a short reply, and refuses a note that is closed, already addressed or not there. It cannot write, edit, close, reopen or remove a note; no other tool reaches the pins, and a chat message changes none. Only the person closes or reopens; rewriting an addressed note opens it again. Every step is appended to the pin's history.

**Undo.** A turn records the notes it marked addressed (`Turn.addressed`: the note's number and the place of the `addressed` entry in its history). "Undo this turn" takes them back with the prototype, as one step: each such note is open again and its reply is dropped from the note, with an `undone` entry appended to its history, which still holds the reply. It is taken back only while that entry is the last thing that happened to the note: a note the person closed, reopened or rewrote since is theirs and is left alone. A turn that only answered notes can be undone too, while an answer of its still stands. The API history is append-only and is not touched: the agent is told in its next message, where the reopened notes ride again.

**Several notes on one spot.** Notes pinned closer than three quarters of a marker's width share a spot (`spots` in `anchor.ts`). Every marker stays at its own point, in its own shape, and stays a button for the keyboard; the spot gets a count beside the marker on top (a pill with a stack glyph and the number, a Todae `Menu`) that lists its notes with their state. Picking one opens its card and brings its marker to the top. Escape closes the list before it leaves pin mode.

**Variants.** The Variants view takes notes as the board does, with its own "Pin a note" toggle and the same shortcut. "Current" is the prototype, so it shows the board's notes and a note pinned there is the board's. A note pinned on a variant holds the variant's id in its anchor (`anchor.variant`) beside the scenario, view and the spec element's key, and lives in the same `PrototypeRecord.pins`, numbered with the rest: it is listed in "Your notes" with its variant, rides to the agent with its place starting `variant "b"` (the agent changes that variant with `revise_variant`, then answers the note), is placed again on what the variant draws after a revision, and stays in the list, saying so, when the variant is dismissed. A new variant never takes an id a note names. Core's `VariantState` is not touched, and no standing, report or pick reads a note. The combination being picked takes none: it is kept nowhere until applied, and then it is the prototype. A proposal's examples take none either: they are the fixed proof a rule must pass and fail, replaced whole on each revision, and feedback on a proposal already has one recorded channel in core's lifecycle (Send back, with its note in the proposal's history); a second state beside the proposal's status would say nothing core reads.

**A pick takes its notes along.** When a pick is applied, each open or addressed note on a variant moves onto the prototype if that variant gave the slot the note's element sits in (`pick.ts`, `carryWithPick`). Core's `recombinedKey` answers that: it maps the element's key in the variant's expanded page to its key in the combination (a key two sources bring is renamed for its source, and what a layout instance draws follows its instance), or says the pick did not take it. The note drops `anchor.variant`, names its element by the new key, keeps its number, words, state, reply and history, and gains a `picked` entry ("You applied a pick from Variant A: the note came with it, onto the prototype"). The board then places it on the new revision by the rules above, like any note of the prototype. A note on a slot the pick did not take stays on its variant; so does a closed note, a note already "moved or gone" on its variant, and a note on the bare page unless every slot came from its variant. The confirmation says how many came along, and the agent is told with the pick. **Undo this pick** puts every note that pick moved back on its variant with the anchor it had there, kept in the `picked` entry (`returnFromPick`), and appends `unpicked`; only the place is put back, so a reply, a rewrite or a close since then stays. The pick's own time (`PickRecord.at`) names its notes, so core's pick record holds nothing of them, and no report, standing or pick verdict reads any of this. A turn's undo (above) no longer takes back an `addressed` entry once a pick has moved the note, since that entry is no longer the last.

**Storage.** Pins are saved with their prototype in IndexedDB at once, and exported and imported in the project file (`pins` beside `prototype`); both readings validate every field (`parsePinState`), report what cannot be read, and never drop it silently. The format is still version 1 with optional additions, each validated strictly: `anchor.variant` (a variant id; refused with a TSX source), `source.elsewhere` on a `source` of kind `"source"` only (at most 256 strings of 8 lowercase hex digits), and the history entry `{ "kind": "undone", "at", "by": "you" }`, accepted only straight after an `addressed` entry, and the entries a pick writes: `{ "kind": "picked", "at", "by": "you", "variant", "from" }`, where `from` is a whole anchor on that variant, and `{ "kind": "unpicked", "at", "by": "you", "variant" }`. The two alternate in a note's history, an `unpicked` names the variant of the `picked` before it, a note whose last of them is `picked` has no `anchor.variant`, and one whose last is `unpicked` is on that variant; anything else is refused. An app from before these reads a file without them and refuses one with them. A `source` of kind `"source"` (a place in a TSX file) is read and then dropped, its pin marked lost; the app writes only `"key"` sources now.

**Built with Todae.** `Button` (the toggle, with `pressed`), `Menu` (a spot's list of notes), `Popover` and `usePopover`, `Field.Textarea`, `Field.Select`, `Badge`, `Card`, `Disclosure`, `Stack`, `Text`, `useHotkey`. Gaps: Todae has no pin or annotation-marker part, so the marker is a plain `<button>` styled on tokens; `usePopover`'s `anchorRef` is read once per open, so each marker owns its own popover rather than one popover moving between markers; there is no token for a colour that is neither brand nor status, so `harness.pin`/`harness.note` take Todae's violet scale directly. `Menu` always gives focus back to its trigger when an item is chosen and has no option to send it elsewhere, so a spot's list moves focus to the picked note's marker a frame later; and the trigger has no small size, so the count is sized to a marker through the `--todae-button-*` variables.

**Not built.** Pins on a proposal's examples and on a combination not applied yet (see Variants). Dragging a pin to another spot. A pin on a frame not measured yet.

## Storage and the project file

IndexedDB database `design-harness`: `projects` (by id) and `prototypes` (by project and id). What is read back is validated with core again, and a record that no longer validates is reported, not loaded. A stored TSX prototype is kept as it was, for its files alone, and a config's rules only TSX had are taken out first ([TSX prototypes, notice only](#tsx-prototypes-notice-only)). Export writes `<project id>.design-harness.json`:

```json
{ "format": "design-harness/project", "version": 1, "project": { "...": "the ProjectConfig" }, "prototypes": [{ "id": "booking", "name": "Booking", "prototype": { "...": "the Prototype" } }] }
```

A prototype with [pinned notes](#pinned-notes) carries them as `"pins"` beside its `"prototype"`, history included; one without has no such key.

Import refuses the file whole on any problem, listing every one with its path (core's config and prototype validation, unknown fields, duplicate ids; a TSX prototype that is whole is kept for its files, and rules only TSX had are taken out with a notice), and otherwise replaces the stored project of that id with exactly the file's prototypes. It then opens that project; the other projects in the browser stay as they are ([Projects](#projects)).

## Library versions

A project names its library at one exact version, and the frames render that version, not the app's own. Before this, the vendor build served only the version installed, while the app still described and migrated projects on Todae 0.10.1: such a project validated and checked, and every frame said "the local package source has @tounsoo/todae 0.11.3, but the project asks for 0.10.1".

- **Every described version is served.** `designHarness.libraries` maps each package to the exact versions served, each with its stylesheets: `"@tounsoo/todae": { "0.11.3": ["dist/todae.css"], "0.10.1": ["dist/todae.css"] }`. One version is the app's own dependency; each other is installed as an npm alias named `<package>-<version>`, here `"@tounsoo/todae-0.10.1": "npm:@tounsoo/todae@0.10.1"`. The alias is derived from the name and version, so the config never repeats it, and it says what it holds in `node_modules` and the lockfile. The vendor build builds each version from where it is installed and files it under its real name and exact version, so a frame imports `@tounsoo/todae` and gets the version its project names. React stays one instance, external to every library version; the build refuses a version whose React peer range the served React does not meet. Each version has its own stylesheet file. The alias also installs a second `todae-tokens` bin, so `npm run tokens` calls 0.11.3's builder by path.
- **Described but unrenderable fails the build.** `src/libraries/versions.test.ts` holds every description in `packages/core/libraries/`, every registry entry, every version `migrate.ts` accepts and every version a project can move to, to the declared config, and each to the version installed; it needs no vendor build. `build-vendor.mjs` itself refuses a manifest that leaves out any of core's descriptions.
- **A version still not served says so.** An imported project on a version nobody vendored fails every frame with "What you can do is above the canvas", and the notice there names the version asked for and the ones served, and offers to move the project to a served version, or, unless the build sets `VITE_ESM_FALLBACK=off`, to load that exact version from esm.sh for this project only (above). Nothing loads from esm.sh until a person chooses it.
- **Moving a project to another version.** From the notice or the Project view's Component library section: pick a version the app describes and serves, and core's `planLibraryMove` shows what changes before anything does: parts added, removed, changed and likely renamed, whether every role mapping still names parts and values the new version has, inventoried components it lacks, style props it adds, and, for every prototype in the project, how core's report changes, checked by code on both versions without measuring (the canvas measures the rendered rules after the move). A refused move says why and has no confirm. On confirm, `moveLibrary` changes the version, its parts and stylesheets, and records the move in `library.history`; nothing migrates a stored project by itself. It is not a proposal: a move changes neither the inventories nor the rules, so there is no rule to prove on examples; a component the new version lacks is removed by a proposal first.

The second Todae adds 681 kB to `public/vendor/` (405 kB of JS, 132 kB gzipped; 276 kB of CSS, 36 kB gzipped), fetched only by a project on 0.10.1: the folder goes from 2,405 kB to 3,087 kB. The app's main chunk goes from 1,819 kB to 1,868 kB minified (509 kB to 524 kB gzipped): the move, the notice, and core's role drafter and the registry, which the move needs and which leave the New project chunk (78 kB to 43 kB), so the app's JS as a whole grows by 14 kB.

## Known gaps

- A lens shows two rule families, tap targets and the first view. Reading order, the primary-action spotlight and the slot map need more than the snapshot holds (boxes for slots and layout containers), and are not built.
- A lens is not drawn on the frames of the Variants view or of a proposal's examples, only on the board.
- The first-view lens finds what crosses the view's edge among what the snapshot holds: controls, headings and text. A wide plain box is not in the snapshot, so the strip can stand with nothing outlined.
- The contrast figure shows the schemes in which core found the text failing. A scheme where it passes has no finding, so no row.
- A stored project keeps the views it was saved with: the seed's dark views reach a new browser profile, not a project already in IndexedDB.
- esm.sh is unverified (above). The local source serves only installed versions and root entries.
- A library move keeps the project's React, root part and scheme attribute; a version that changes those needs a new project. Its dry run checks prototypes without snapshots, so a change only the rendered rules would see shows after the move, on the canvas.
- Element tags (above) read React's fiber tree (`child`, `sibling`, `tag`, `stateNode`, `memoizedProps`, the fiber root's `current` and the container's `__reactContainer$` key), fields React has kept since 16 and 17 but does not document; another React could need `frame/tags.ts` to change, and until then frames would report no tags and findings would say they are not drawn.
- A spec element in a repeat over a known list is one key, so a finding about one item outlines every item. Spec layout instances have keys of their own, so two instances never share an outline.
- A finding the `extract` rule reports and a finding about an element core cannot expand have no targets and point at the file only.
- The outline is sent when a finding is selected; a frame that finishes measuring later is not outlined until the finding is selected again.
- A layout parameter cannot stand in a `visible` condition or inside a `$template`; the page gives the whole prop's value instead.
- A new prototype starts empty; the agent or the code view builds its first page and flow.
- New project uses a library the deployment ships, or an imported description of one its package source can load; a library the deployment does not serve stops at the library step ([New project](#new-project)). The wizard does not keep its answers across a reload.
- A library request ([Requesting a library](#requesting-a-library)) is pending until a person reloads after the deploy; the app cannot ask GitHub how it went. The workflow adds only a library whose every role core can draft, and infers no light and dark switch for a new package. The describer's `--before` is one second after the version was published, so a package whose own dependencies were published moments later in the same release (Blueprint 6.23.1 and its icons) cannot be described. The workflow cannot run until it is on the default branch: it was run step by step on one machine, against the real npm registry and a fake GitHub API.
- A role's preview is composed from part names (a family's root around its item, a summary beside a panel, a label for a field). A library built another way may not draw, and the frame then says which part could not render; the mapping can still be confirmed.
- The wizard asks for tasks, ranked actions and caps. Page types, views, disclosed sections and layouts start from core's fixed set, and change afterwards by proposal or by importing an edited project file.
- Opening New project closes the open workspace, so an agent turn that is running stops, as it does on a reload.
- A project cannot be renamed or deleted in the app yet.
- A stored TSX prototype cannot be converted to a spec; it is kept for its files, and a spec version starts empty.
- The code view is a textarea with one marked line.
- The agent has been run only against the fake API (The agent, above).
- The chat renders the agent's text as plain text, not Markdown.
- Undo restores the prototype as it was before a turn; an edit made by hand in the code view after that turn is undone with it.
- The default shell is generic: no per-page-type shell code and no prototype-wide frame yet.
- Rendered measurements depend on the browser: fonts and scrollbar style differ between machines, so a report is reproducible on one browser and machine, not across them.
- The review page measures every example in every scenario and view, so a proposal with many examples holds many frames (Nook: 16 per example). They render a dozen at a time (`runtime/render-slots.ts`), so they all measure, but nothing limits how many a page holds.
- The agent's dry run reads source only, with no frames: for a rendered rule, the first verdict with measurements is the review page's. The same holds for the checks `propose_variants` returns: the Variants view measures them.
- Variants and slot picks are for spec prototypes only. The Variants view renders every source in every scenario and view (Nook, three variants and a combination: 80 frames); they render a dozen at a time, and nothing limits how many the view holds.
- Recombination takes each slot's elements as the source lists them; elements outside every slot are left out unless every slot comes from one source.
- Code export writes what core read: a part of a spec the catalog refused is not in the export, and its README says so.
- The project's other prototypes are measured for the impact while a review page is open, but only the open prototype is re-checked on the board after an adoption; another prototype's checks run when it is opened.
- A send-back is recorded in the history before its chat message is sent; if the request then fails, the note stays recorded and the turn shows the error, with Retry where it helps.
- The loop's note matching is word overlap, not meaning: two notes that say the same thing in different words are not a pattern, and two that share two words by chance are. Its thresholds are fixed at two, and it reads the open prototype's chat and the project's send-backs, not other prototypes' chats. A turn's starting state is known only when every frame had measured the prototype when it started; otherwise only the rules its own checks failed count as fixed.
- An adopted proposal's examples keep the snapshots measured at adoption: if the project's views or library change later, re-running them reports the missing views as not measured rather than measuring again.

## The Project tab

`ProjectView.tsx` shows the project as pictures, each drawn from the config or from core's facts with the same words beside it, and decides nothing.

- **The palette** (`Palette.tsx`): every inventoried component is a tile holding the component drawn by the project's own library and version, from the spec core's `partSpecimen` writes. The app never draws a part itself: a component core cannot compose shows its name and "No specimen" with core's reason, and a layout-only part is drawn holding three of the library's own small parts, which the tile says. Under each frame: the name, how many parts it has, and each drawn sample with the roles it carries as tags (`library.roles`) and the rank of the ranked action written on it (`inputs.ranking`). A role no tile carries is listed in words (`unplacedRoles`). A shipped library's `partProps` (the registry's, as in the wizard) are passed through.
- **Frames**: one per tile, sandboxed exactly as the board's are (`FrameViewport`, a `Session` from `createSession`: `allow-scripts` alone, the same document, nonce CSP with `connect-src 'none'`, and protocol). A tile's session is made only once the tile has been scrolled near (`useSeen`, an `IntersectionObserver`), and its frame renders through the shared `RENDER_SLOTS`, so a long palette costs what is on screen.
- **Page types** as slot diagrams: slots in the order the project lists them (not a promise about where each renders), chrome hatched, the primary slot heavy with a button in it. The diagram is an ordered list, so a screen reader reads the same slots and kinds.
- **Rules in force** as cards grouped by what a rule looks at ("How many on a page", "What sits where", "As rendered", "From the inventory", "The flow", "In the code"). `ruleGroup` and `ruleGlyph` derive the group and the glyph from `rule.type` and `check` alone, so a rule a proposal adds is grouped and drawn the day it is adopted; a rule type core adds fails to compile there until it has a group. Only a rule about how a rendered page looks has a glyph (a control's size, text on its ground, the heading outline, the first view's end, sideways scroll): there a picture shows what words can't. A count, a place, a list, a flow, a name or a rule about code reads whole in its sentence and draws nothing, because a generic picture would only repeat it. A glyph shows the rule's shape, not a page of the prototype, and is hidden from a screen reader: core's `describeRule` words are beside it. A rule from an adopted proposal names its stored examples and links to the proposal.
- **Tasks and limits**: each task's step budget in words ("at most 3 steps"), each cap as its limit in words with which way is stricter and the rules that read it, the ranked actions in order, and the sections always behind a disclosure. A count is a number and has no picture. A `_PX` cap is a length, which words cannot show, so it is also drawn as a square at its actual size.
- **"Today" lines** are about the open prototype and named for it: under a task's budget is what core's `flowFacts` says its longest route takes ("Booking's longest route today: 3 steps, at the limit."), and the flow map under the cards draws that route. With no prototype open they are absent. Caps have no "today" count: core's `count-vs-cap` evidence is on findings only, so a count exists only once a cap is already exceeded.
- **Proposals** is a five-item timeline of the newest proposals with a link to the Proposals tab, which is their home.

Built with Todae: `Card`, `Badge`, `ToggleGroup`, `Disclosure`, `Table`, `DataList`, `Text`, `Code`, `Button`, `VisuallyHidden`. What Todae has no part for, done in `app.css` on the harness tokens: the specimen tile (the library's ground over the app's), the role tag with a pointer, the slot diagram, the class scale, the status track, and the rule glyphs.
