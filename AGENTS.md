# Agent notes

design-harness is a browser-only web app for prototyping product UI with an agent, inside guardrails. It has the core library, `packages/core`, and the web app, `apps/web`: the shell, the canvas, a code view, and the agent chat on the person's own Anthropic API key.

## Set up

Node 22. `npm ci` from the root installs every workspace (`packages/*`, `apps/*`). `.npmrc` sets `legacy-peer-deps`.

## Check

```sh
npm run check
```

It runs `typecheck` (each workspace's `tsc`: the library against the ES2022 lib only, its tests with Node types; the app against the DOM, its tests with Node types too), `lint` (ESLint) and `test` (Vitest, core's tests and the app's unit tests, one of which fails when the built token layer is stale). CI runs `npm ci && npm run check` as its `check` job, and the end-to-end tests below as its `e2e` job, on every pull request and every push to `main`; the `e2e` job has 30 minutes. `npm run bundle:core` bundles the core library for the browser, prints its size, and fails if anything from `node_modules` is bundled into it.

```sh
npm run e2e
```

builds the app and runs `apps/web/e2e/run.mjs` in Chromium: every frame of the Nook spec renders, the legal prototype passes every rule, a violation injected into a spec is marked on its JSON line and outlined in every frame that draws its elements, the same prototype gives the same report on reload, export and import round-trip, packages load by URL from a CDN-shaped origin, Tally renders on Mantine and carries the target-size and contrast tests, a frame cannot reach the app (a spec with hostile text, and code run inside each frame), a stored or imported TSX prototype is notice-only, variants are compared and picked, code export builds, a stored project keeps the library version it asked for and moves to another only on confirm, checks give the same report, byte for byte, in the worker and on the main thread for Nook and Tally, the visual checks' figures and lenses change no report, the shell at phone, tablet, laptop and desktop widths, the Variants view, the Proposals view, a review page and the New project wizard at 390 px wide, the new project wizard, a library request, a person removing or changing a rule from its card and changing a task's step budget from the Project view, each through a proposal, pinned notes (pinned, sent to the agent, addressed, closed, kept across reload and export and import, moved or gone, on a parked frame, by keyboard alone, two on one spot, opened again by undoing the turn that addressed them, on a variant, moved onto the prototype by a pick and back by its undo, with the report unchanged byte for byte), and the agent's whole loop runs against a fake Anthropic API at api.anthropic.com's address (spec edits, failing checks fed back, proposals, stop, errors, refusals, undo, and the key's absence from frames, exports and storage). It uses `playwright`, pinned as a root dev dependency, with the Chromium at `/opt/pw-browsers/chromium` when that exists and Playwright's own Chromium otherwise. CI's `e2e` job installs that Chromium with `npx playwright install --with-deps chromium`. Run it before pushing a change to `apps/web` or to what core says about rendered pages. `node e2e/run.mjs "<part of a test's name>"` in `apps/web`, after `npm run build`, runs the tests whose names hold those words. `E2E_SCALE=2` saves its screenshots at twice the density and changes no CSS pixel a test reads. `node e2e/board-performance.mjs` and `node e2e/lens-performance.mjs`, after a build, measure how heavy a board is and what the lenses cost; they are not in CI. Two full e2e runs at once on one machine starve each other and fail with `page.goto` or measuring timeouts: run one at a time. CI's fonts are not the local ones, so a test never asserts a size that depends on text metrics; it reads sizes from the page or from core.

Its helpers, in `run.mjs`: `measured(page, revision)` waits for core's report on a revision with every frame's answer; `eventually(page, read, accept, message)` reads until a value is accepted, for what the app sets a tick after a click or a key, where a read straight away can miss; `mainView(page, name)` is a main view's button (Canvas, Variants, Project, Proposals: the main views are a toggle group, not tabs); `showAllRules(page)` opens the Checks tab's Details, where every rule in force is listed. The Checks tab leads with what to fix, so a test that reads a rule's row calls `showAllRules` first. Only frames near the view are live; the rest are parked, showing their last snapshot with no iframe. `liveFrame(page, title)` scrolls a frame on screen, waits until it is live and drawn, and returns it; `everyLiveFrame(page)` visits every frame of the board in turn. A test that reads a frame calls one of them first, and one that counts frames counts `.frame-viewport`, not iframes. The Project view's palette draws each part in a frame named "<component>, drawn by <package>", so a count of the board's frames leaves out `[data-frame-name*="drawn by"]`. `importNook(page, prototypes, project)` imports the seed with prototypes that each change Booking's booking page (`change`) or its flow (`flow`), and optionally the config, and waits until the first is measured; `approveAndAdopt(page)` approves and adopts the open review page's proposal, waiting for its examples to be judged when it has any; `importWithTsx(page)` imports the open project again with a stored TSX prototype. At narrow widths, `headerIsLaidOut(page, where)` fails when header parts overlap, leave the window or are under 24 by 24 CSS px, `noSidewaysScroll(page, where)` when the page scrolls sideways, `narrowIsUsable(page, scope, where)` when a control in `scope` is under 24 by 24, cut off or out of reach, and `reachable(page, control, where)` when a control is not inside the window and uncovered; `shotNarrow(page, name, drawn)` screenshots the page at tablet and then phone width.

```sh
npm run tokens --workspace @design-harness/web
```

rebuilds the app's token layer after a change under `apps/web/tokens/`. Commit what it writes in `apps/web/src/theme/`.

## Deploy

GitHub Actions builds and deploys; Vercel never builds. After `check` and `e2e` pass, CI's `deploy` job downloads the exact `apps/web/dist` the end-to-end tests ran against, turns it into Vercel's prebuilt output with `scripts/vercel-output.mjs`, and runs `vercel deploy --prebuilt` with a pinned CLI. A pull request from this repository gets a preview deployment and a push to `main` deploys production; both show as GitHub environments with their URL. The Vercel project `design-harness` is deliberately not connected to the Git repository, so Vercel cannot start a build of its own. Do not connect it. The job needs the `VERCEL_TOKEN` repository secret; without it, the job assembles the output and says it deployed nothing. A project whose library version this deployment does not serve can choose to load it from esm.sh (`library.source`); a build with `VITE_ESM_FALLBACK=off` takes that choice away. CI's build does not set it.

## Library requests

A designer asks for a library this deployment does not serve from the New project wizard, which opens a prefilled GitHub issue (`.github/ISSUE_TEMPLATE/library-request.yml`). `.github/workflows/library-request.yml` runs on an issue labelled `library-request`, over `apps/web/scripts/library-request.mjs` and its input check, `library-request-input.mjs`, which the wizard shares: it validates the request, checks the exact version on npm, describes the package, adds it to `designHarness.libraries` and the registry, runs the checks, the build and the e2e test `a requested library` (which exists only when `E2E_LIBRARY` is set), and opens a pull request. Issue text is untrusted: no `${{ github.event.issue.* }}` expression, every job re-validates the event file, and the package installs with `--ignore-scripts`. A pull request the workflow opens comes from its token, so CI does not run on it; the workflow ran the checks itself, and a push to the branch starts CI.

## The two rules not to break

1. **Checks are deterministic.** A check is a pure function of the project config and the prototype that returns findings: same input, same output, in the same order, whatever order keys, files or rules come in. No model, clock, randomness, network or file system anywhere in the checking path. Library code under `packages/core/src` must also run unchanged in a browser and in Node: no `node:` imports, no DOM globals. ESLint fails a change that reaches for them, and `packages/core/test/browser-bundle.test.ts` runs the browser bundle in a realm with neither.
2. **A proposal becomes a check.** A proposal carries the inventory change, the rule that governs it as data in the fixed rule vocabulary, and examples that must pass and must fail. It is adopted only when its rules pass the passing examples and fail each failing example for the named rule's reason alone; a proposal that only removes rules (`onlyRemovesRules`) needs no examples, and any it carries are still judged. Once adopted, the rule runs on every prototype in the project, and its examples stay as regression tests (`rerunExamples`). A rule changes or leaves force only through a proposal: a person starts one from a rule's card or a task's step budget, or the agent drafts one, and only a person approves and adopts it. Nothing in the app edits `config.rules`.

When core cannot resolve something in a spec that a rule depends on, the rule reports that it cannot be checked. Never let it pass silently.

## Where things live

- `packages/core/src/config/`: the project config types, schema and cross-reference checks.
- `packages/core/src/prototype/`: the prototype, spec only (`format: "spec"`), and the page model every rule reads (`model.ts`). Stored data that says it is TSX is refused with `TSX_REFUSED` and handed back as a `TsxPrototype`, so the app can show and export its files.
- `packages/core/src/rules/`: the rule vocabulary as types and schema, and `bounds.ts`, a rule's limits (`min`, `max`, `depth`, `minPx`): `ruleBounds`, `withRuleBound`, `boundValue`, `boundWords`, `compareRules`. `src/builtins.ts` is the built-in rule set.
- `packages/core/src/engine/`: selector matching, one evaluator per rule type in `rules/`, a rule in plain words (`words.ts`), and the report. A finding about elements lists them as `targets`, each where it is written, the page it is on and its key in the expanded page, so the app can outline each wherever it renders. `evidence.ts` is the numbers a finding carries for a picture, with each rule type's kind (`RULE_EVIDENCE`); `facts.ts` gives the same verdicts for a whole page or flow, passing parts included.
- `packages/core/src/rendered/`: the rendered snapshot type and its arithmetic.
- `packages/core/src/proposals/`: proposal operations (`opLabel`), classification and lifecycle. `classify` reads a rule removed and added again under the same id as one change: `tightens` when every limit moved the stricter way, otherwise `loosens-or-removes`; a classified change keeps `rule`, `was` and `bounds`, and a `set-max-steps` change its `bounds`, so an adopted one stays readable. `proposalImpact` gives each prototype before and after a draft, and the adopted examples it retires or breaks; `onlyRemovesRules` says a proposal only removes rules.
- `packages/core/src/spec/`: the spec prototype format: the catalog the project config generates, a JSON parser that keeps every key's position, spec validation, and conversion into the page model every rule reads. `docs/trials/json-render.md` records the trial that led to specs, and the move to specs only.
- `packages/core/src/variants/`: variants of a spec page (validation, storage shape), `recombine`, a page built slot by slot from several, which also says where each source's elements went (`keys`, and `recombinedKey`, a source's key in the result), and `pickScope`, which sorts a report into what a pick on one page answers for: the page's own findings, what the change brings elsewhere, and what another page already had.
- `packages/core/src/library/`: onboarding a component library: `draftRoles` drafts a role mapping from a library description, with confidence and evidence, `confirmRoles` turns a person's confirmation into the config's `roles` and `excludedProps`, and `missingRoleEffects` says what each rule needing a missing role will do. `project.ts` is what the New project wizard computes, from a role draft to a config with a starter prototype that passes every rule (`buildProject`). `move.ts` moves a project to another library or version: `compareLibraries`, `planLibraryMove` (what each prototype's report would gain or lose), `moveLibrary`, `chooseLibrarySource`, `mappingProblems`. `specimen.ts` draws one part with its roles' samples for the palette (`partSpecimen`), and `unplacedRoles` says which roles the palette cannot place. `packages/core/scripts/draft-roles.mjs` runs `draftRoles` and `confirmRoles` on the command line. In the config, `library.excludedProps` names the library's style props, which no prototype may set (the catalog refuses one), and `library.root` a part every page renders inside, such as Mantine's `MantineProvider`. `library.source` says where a frame loads the library (this deployment, or `"esm.sh"`), and `library.history` records each move and source change.
- `packages/core/src/export/`: code export: a spec prototype written as TSX (`specToTsx`), and a prototype as a runnable React project (`exportReactProject`), which writes a stored TSX prototype's files as they are.
- `packages/core/libraries/`: descriptions of a component library's parts and props, written by `packages/core/scripts/describe-library.mjs`, which a project config's `library.parts` carries.
- `packages/core/examples/nook/`: the worked example project and its legal, illegal and refused spec prototypes (`prototypes/spec/`), which are the engine's regression fixtures.
- `packages/core/examples/tally/`: the second worked example, on Mantine: its config, the Mantine parts it carries, its confirmed roles (`roles.json`), and its legal, illegal and refused spec prototypes.
- `packages/core/test/library-fixture/`: a library's declarations alone, every kind of part and prop the describer reads, for its tests.
- `scripts/vercel-output.mjs`: turns the built app into Vercel's prebuilt output, with its headers.
- `packages/core/README.md`: the config, the rule vocabulary and the proposal lifecycle.
- `apps/web/`: the browser app. `src/app/` is the UI, built with Todae: the canvas first, with the chat, the checks and the code as panels around it, and `words.ts` for the plain words a designer reads (a scenario by its page and state, a rule's lead), ids staying in Details and code; `RuleChange.tsx` and `BudgetChange.tsx` the dialogs that start a proposal to remove or change a rule from its card, or change a task's step budget, on one shared shell, with `project-measure.tsx` measuring every spec prototype for their impact; `shell-width.ts` the shell's width (phone, tablet, laptop or desktop, from the `harness.shell` tokens), set on `.shell` as `data-width`, which the CSS styles on; `src/visual/` the visual checks, drawn from core's evidence and facts and deciding nothing (the figure registry, where each evidence kind has a figure or is words only, because a count, cap or budget is shown as words and a picture is drawn only where it shows what words can't; the lenses over the artboards; the coverage grid; the flow map; where "Show me" moves the canvas); `src/pins/` pinned notes (the note and its history, anchoring to a spec element's key and re-anchoring, notes that share a spot (`spots`), a note on a variant (`anchor.variant`), `pick.ts`, which moves a variant's notes with a pick and back on its undo, the words the agent gets, the layer over the artboards, "Your notes"); `src/review/` a proposal's review (the actions, each a step of core's lifecycle by "you", the history, with `ownProposal` for a proposal a person started, the inventory diff) and the models of the rule and step-budget dialogs (`rule-change.ts`, `budget-change.ts`); `src/agent/` the agent (the API client and request, the tools and their input validation, the append-only history, the turn loop, the key vault); `src/runtime/` the parent side of the frames (the check session, the frame protocol, the frame document and its sandbox, the package sources, `live-frames.ts`, which keeps at most `FRAME_BUDGET` frames live and parks the rest, `check-engine.ts` and `check-worker.ts`, which run core's checks in a module worker, or on the main thread when the page is opened with `?checks=main` or a worker cannot start, and `tags.ts`, the element tags: the one prop that says which spec element, by its key, a part came from, and the plan of which frames outline a finding's `targets`); `src/frame/` what runs inside a frame (the boot script, the spec renderer, which draws a spec through json-render with no prototype code, the page kit `@design-harness/page` and its default shell, the snapshot collector, and `tags.ts`, which finds what each tag drew in React's tree, never the DOM's attributes; the snapshot message carries `places`, the box each tag drew, beside the snapshot, never in it); `src/store/` IndexedDB (projects, prototypes with their variants, chats), the project file, and `migrate.ts`, whose `withoutTsxRules` takes the TSX-only rules out of a stored or imported config before core reads it; `src/export/` the code export's zip; `src/libraries/` the component libraries the deployment ships, which the New project wizard offers, `versions.ts`, the versions served, and `requests.ts`, the library requests pending in this browser; `src/app/LibraryVersion.tsx` the move between versions, `LibraryRequest.tsx` the request form, and `Palette.tsx` and `ProposalPreview.tsx` with `src/visual/project-model.ts` and `project-figures.tsx` the Project and Proposals views drawn as pictures; `src/seed/` the Nook project a first open starts with, its spec Booking prototype only; `e2e/` the end-to-end tests and `e2e/fake-anthropic.mjs`, the fake Anthropic API every agent test runs against; `test/` helpers for the app's unit tests. `apps/web/README.md` documents the agent, the frame protocol, the scenario contract, the package-source interface, the isolation model and the widths.
- `apps/web/tokens/`: the app's token layer on Todae's tokens, a DTCG resolver (`resolver.json`) over the harness's own tokens (`harness.json`), the contract and button overrides and the light and dark appearances. The harness tokens include `harness.pin` and `harness.note`, the pinned notes' colours and sizes on Todae's violet scale, `harness.shell.*`, the shell's breakpoints, `harness.size.picker-compact`, a picker's least width in the phone's header, and `harness.size.target`, the 24 px least size of a control. The `tokens` script builds it into `apps/web/src/theme/` (`todae-theme.css` and its types) with the installed Todae's token builder, called by its path, and `src/theme/theme.test.ts` fails when those files are stale. `src/app/app.css` lays the app out with Todae's `--todae-*` variables and the harness's `--todae-harness-*` tokens, never raw values: a size the layout needs is a token first.
- `apps/web/package.json`, `designHarness.libraries`: the component libraries a frame can load from this repository, as a map from each package to the exact versions served, each with the stylesheets a project may name. One version is the app's own dependency; each other is an npm alias named `<package>-<version>`. `apps/web/scripts/vendor-libraries.mjs` reads the map, and `apps/web/scripts/build-vendor.mjs` prebuilds every version, with React and json-render, into `public/vendor/`, where the manifest files each under its real name and version. A unit test fails when a library description the app ships names a version that is not served. The library-request workflow appends to the map and the registry.

Nothing in `apps/web` decides pass or fail: it renders, measures and shows `checkPrototype`'s report unchanged, and the agent gets that report; no model decides. Core reads specs only, and no prototype code runs: a spec is data. What does run in a frame (the boot script, React, the library, json-render and the spec renderer) runs sandboxed without `allow-same-origin`, and talks to the app only by validated `postMessage`; keep it that way. The agent writes specs only. A stored or imported TSX prototype is notice-only: its files and a notice, with no board and no checks, and it takes no turn, tool, pin, variant or check. The API key stays in the app's memory and its own IndexedDB database, never in a prototype, export, frame, log or error message. Tests never call the real Anthropic API. A pinned note is a person's feedback kept beside the prototype (`PrototypeRecord.pins`), a note on a variant included: core never reads it, it changes no report, and it starts no revision. Proposal examples and a combination of picks not yet applied take no notes. The agent's only tool for notes is `address_note`, which marks an open note addressed with a reply; only a person edits, closes or reopens one. Undoing a turn opens again the notes it addressed, unless the person has acted on them since. Applying a pick moves the notes on what it took onto the prototype, and undoing the pick puts them back.

A new illegal fixture is a folder under `packages/core/examples/nook/prototypes/spec/illegal/` (`spec/refused/` for what the catalog refuses), or the same folders under `examples/tally/prototypes/`, with a `case.json` (what it shows, and the rule and message fragment that must flag it) and the files it replaces under `files/`. It must fail for that reason and no other.
